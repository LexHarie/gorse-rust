# WP-1-17 notes (data types)

Provisional ids only. The integrator folds these into PORTING.md and
PORTING_NOTES.md at merge and deletes this file.

Go source: `storage/data/database.go` @ add21b5 (record types, patches,
`ValidateLabels`, `SortFeedbacks`). Rust: `crates/gorse-storage/src/data/types.rs`,
`crates/gorse-common/src/gosort.rs` (new, Go's `sort.Sort`).

## Decisions

- **D-WP117-1 `Labels` is Go's `any` as a Rust enum.** Labels reach Gorse as two
  Go types. The REST decoder (go-restful v3.13.0, `entity_accessors.go:138`)
  calls `UseNumber`, so its numbers are `json.Number`. gorm's JSON serializer
  (gorm v1.31.1, `schema/serializer.go:95`) calls `json.Unmarshal`, so values read
  from the database are `float64`. `ValidateLabels` treats the two differently
  (it accepts `json.Number`, rejects `float64` and `bool`), so the enum keeps
  `Number(String)` (text) and `Float64(f64)` apart. `Deserialize` gives
  `Float64`, which is `json.Unmarshal`'s default. The REST path needs its own
  `UseNumber` decode (Q-WP117-5).
- **D-WP117-2 `Categories` is `Option<Vec<String>>`.** Go's nil slice marshals
  as `null`, and an empty slice as `[]`. Both occur: a REST body without
  `Categories` gives nil, and `sql.go` writes nil as `"null"`. A `Vec` would
  change the wire output. `ItemPatch.Categories` uses the same type, because
  `patch.Categories != nil` is how Go decides to update.
- **D-WP117-3 `Labels::Nil` means unset in patches.** `ItemPatch.Labels` and
  `UserPatch.Labels` are not `Option`. Go's `patch.Labels != nil` treats a nil
  `any` as unset, and `Labels::Nil` is that value.
- **D-WP117-4 Go's `sort.Sort` is ported, not Rust's sort.** `sort.Sort` is
  pattern-defeating quicksort and not stable. `SortFeedbacks` decides which
  feedback is latest when timestamps are equal, and `logics/recommend.go`,
  `worker/pipeline.go`, `server/rest.go` and `master/rest.go` all sort with it.
  Up to 12 elements it is an insertion sort, which is stable, but above that the
  tie order depends on the exact sequence of Less and Swap calls. So
  `gorse_common::gosort` is a port of go1.27.0's `sort.go` and
  `zsortinterface.go` (`Sort`, pdqsort and its helpers). It is a shared module
  for later packages, which also call `sort.Sort`.
- **D-WP117-5 `ScanOptions`, `ScanOption`, `GetOptions` are not in this WP.**
  They are query options of the `Database` interface, not record types, and
  WP-2-1 ports them with the interface. `NewScanOptions` and the `With*`
  functions go there too.

## Evidence

- `cargo test -p gorse-common --test gosort_golden` and the `heap_sort_matches_go`
  unit test: 1000 cases of `sort.Sort` and 1000 of a verbatim copy of go1.27.0's
  `heapSort`, written by `contracts/tools/sortgolden` (`go run ./contracts/tools/sortgolden`).
  Each case is a slice of keys with repeats, in both directions, with sizes 0..40
  and up to 1000, and key patterns that exercise insertion sort, the ninther,
  breakPatterns, partialInsertionSort and partitionEqual.
  Mutation checks: removing the breakPatterns body fails 110 cases; disabling
  the shifts in partialInsertionSort fails 3 cases. Both were restored.
- `cargo test -p gorse-storage --test data_types_golden`: 19 JSON round trips
  and 26 `ValidateLabels` cases, written by `contracts/tools/datatypesgolden`
  from Go's `json.Unmarshal`, `json.Marshal` and `data.ValidateLabels`. Mutation
  checks: unsorted map names fail the golden, and so does serializing
  `UpdateAt`. Both were restored.
- `cargo test -p gorse-storage data::types`: the two backend-free Go tests,
  `TestSortFeedbacks` and `TestValidateLabels`, with the same cases and
  assertions. The Rust `TestValidateLabels` also checks the error texts, and a
  test checks the Go JSON shape of `Item` and `Feedback`.

## Quirks reproduced

- **Q-WP117-1 JSON names are the Go field names.** The records have no JSON tags,
  so `ItemId`, `IsHidden`, `FeedbackType` and the rest are written as Go names.
  Embedded `FeedbackKey` and `Item` are flattened. `UpdateAt` is skipped
  (`json:"-"`). Serde's `rename_all = "PascalCase"` gives these names. Go's
  decoder matches names without case; serde does not (see Q-WP117-4).
- **Q-WP117-2 Map names are written sorted.** `encoding/json` sorts a map's names,
  so `Labels::Object` marshals in sorted order even though it keeps insertion
  order. The golden has an object whose input order differs from its output.
- **Q-WP117-3 An error text lists the labels as JSON.**
  `unsupported labels: [1,"2"]` and `unsupported type in labels: bool` are
  returned to REST callers as the 400 body, so they match Go byte for byte.
  The golden covers HTML escaping inside the list (`<`).

## Open

- **Q-WP117-4 Key matching is case-sensitive, and duplicate names are an error.**
  Go's decoder matches `{"itemid": ...}` to `ItemId`, and takes the last value of
  a repeated name. serde matches exactly and rejects a repeated name. The REST
  decoder (WP-4-x) must handle both, probably with a hand-written `Deserialize`
  on the record types. This WP does not change it.
- **Q-WP117-5 REST labels need a `UseNumber` decode.** `Deserialize` gives
  `Float64`, which is right for the database path. The server WP must decode
  request bodies so numbers become `Labels::Number` with their text, as go-restful
  does, since `ValidateLabels` rejects `float64`. `gojson` and serde do not keep
  number text (`serde_json` would need `arbitrary_precision`).
- **Q-WP117-6 Nesting depth.** Go's `encoding/json` allows 10,000 levels of
  nesting; serde_json stops at 128. Deep labels from a request or a stored row
  fail to decode in Rust.
- **Q-WP117-7 Go's map order in `ValidateLabels`.** Go checks map entries in
  random order, so with several invalid entries Go's error text varies between
  runs. The port reports the first invalid entry in insertion order. The golden
  has at most one invalid entry per map.
- **Q-WP117-8 Go's native `int` labels.** Go code can put an `int` into labels,
  and `ValidateLabels` then says `unsupported type in labels: int`. JSON never
  produces an `int`, so `Labels` has no integer variant. Such values are not
  reachable from the wire or the database.
- **Q-WP117-9 `mapstructure` tags are not ported.** The record types carry
  `mapstructure` tags. The only non-test `mapstructure` decoder in Go that
  touches the data types is in `master/rest.go`, and it decodes config. No
  Rust code needs the tags yet. The stores (WP-2-x) decide if they need them.
- **O-WP117-1 pdqsort's heapSort fallback is not reached by any golden case.**
  `gosort` calls `heap_sort` when pdqsort runs out of its partition budget. No
  golden case gets there. A seeded search of 400,000 random slices of 13 to 24
  keys, and eight structured families up to 400 long, produced no hit. So the
  call from pdqsort is not covered: removing it (the slice is then left unsorted
  on that path) passes every test. `heap_sort` itself matches Go on 1000 cases
  through a verbatim copy of Go's code. To close the gap, an adaptive adversary
  (McIlroy's "killer" for pdqsort) would need to build an input that exhausts the
  budget. Only feedback that defeats pdqsort's pivot choices reaches that path,
  which real data is unlikely to do, but the dataset and logics WPs sort large
  slices, so the gap should close before WP-3-x.
