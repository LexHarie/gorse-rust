## Decisions

- **D-WP41-1: per-user work runs off the runtime.** `Pipeline::recommend` runs each user's job on `spawn_blocking` inside `parallel::detachable`. Async store calls go through `Handle::block_on`. The HTTP rankers (`rank_by_api`) detach their parallel context around the API call, so a blocking request never holds a runtime worker.
- **D-WP41-2: progress.** Progress goes through an unbounded channel to a reporter that pushes `encode_progress` every 10 seconds (Go's tick). Each push is spawned as its own task. Go pushes inline, so this differs only in timing.
- **D-WP41-3: stores.** As in `worker.go`'s sync, the worker connects to `sqlite://` data and cache stores and to `xvec://` vector stores through the master's proxies. Other URIs are opened directly.
- **D-WP41-4: metrics.** `Worker::new` calls `metrics::register()`, which forces every `LazyLock`. `/metrics` lists the worker's gauges from start-up, as Go's `promauto` does.
- **D-WP41-5: binary version.** The worker reports `CARGO_PKG_VERSION` in place of Go's ldflags version.
- **D-WP41-6: config update.** The master's config is unmarshalled into a clone and then set. A failed unmarshal keeps the old config.
- **D-WP41-7: harness, TOML editing.** No TOML crate is in `Cargo.lock`, so `set_key` edits one key's line in one section of `contracts/config/config.toml` and appends the key or section when it is missing. A contract test checks that every key the harness sets exists in the contract file.
- **D-WP41-8: harness, binaries.** `go build` builds `cmd/gorse-master`, `cmd/gorse-server` and `cmd/gorse-worker`. It does not build `cmd/gorse-cli`, which no node needs. The brief's command line includes it.
- **D-WP41-9: harness, Rust worker.** The Rust worker runs in the test process through `gorse_worker::Worker`. No binary is built for it. Its readiness and shutdown use the same HTTP and stop path as the Go worker.
- **D-WP41-10: mixed-test config.** The acceptance test sets `recommend.collaborative.type = "none"`, `recommend.ranker.type = "none"`, and `recommenders = ["latest"]` in the ranker and the fallback. Every other setting comes from the contract. Two reasons: matrix-factorisation training and the FM model make the two runs differ for reasons unrelated to the port, and the candidate set must be deterministic for an exact comparison. The collaborative, FM and reranker paths are covered by the in-process tests (`recommend_collaborative`, `rank_by_click_through_rate`, `rank_by_reranker`, `rank_by_decision`), which check against Go's expectations.
- **D-WP41-11: mixed-test data.** Ten users, thirty items one minute apart in categories `i % 3`, and two `like` feedbacks per user. Timestamps are fixed, so the latest recommender orders items the same way in both runs.
- **D-WP41-12: comparison.** Rows are compared as sorted lists of (item id, score bits, categories). Two lists are equal when they hold the same rows, so this is a comparison of sets with multiplicity. Digests are compared exactly. Dense-vector results are not in this test, so the stable-case rule does not apply.
- **D-WP41-13: `Send` and `Sync` (Q-254).** `lib.rs` has a compile-time check that `Pipeline`, `ItemCache`, `CachedItem`, `Worker`, `WorkerOptions` and `HealthStatus` are `Send + Sync`. WP-4-3 adds its own check for the master.

## Go quirks reproduced (X-WP41-n)

- **X-WP41-1:** `worker_name` is the hex MD5 of hostname, `http_host` and the decimal `http_port`, concatenated.
- **X-WP41-2:** `pull_users` assigns users with the consistent ring of the live peers. If this node is not in the ring it fails with `current node isn't in worker nodes`.
- **X-WP41-3:** the health error body is `{}`. The Rust `HealthError` is an empty struct that serialises to that.
- **X-WP41-4:** JSON responses are sniffed as `text/plain; charset=utf-8`. Errors use Go's `http.Error` form: the message, a trailing newline, and `X-Content-Type-Options: nosniff`.
- **X-WP41-5:** the step-seconds gauges are never added to, so they stay at zero, as in Go. The total-seconds gauge is set at the end of a run.
- **X-WP41-6:** a tick that fired long before it was handled is skipped (`time.Since(tick) <= interval`).
- **X-WP41-7:** a recommend run reports progress every 10 seconds.
- **X-WP41-8 (O-76):** Go's `Recommend` can return a nil list (X-201). **Answer: no difference in the cache.** The SQL store's `add_scores` returns `Ok(())` for an empty slice (`crates/gorse-storage/src/cache/sql.rs` line 872). Go's Redis `AddScores` loops over the documents, so it sends nothing for an empty list. Both sides then run the stale-row delete. A nil and an empty list therefore produce the same cache rows. The Rust Redis and Mongo paths were not read for this answer.

## Deviations (D-WP41 and X-WP41)

- **X-WP41-9: `serve` was not `Send` (fixed).** The unit tests never spawned `serve`, so this was not caught until the harness spawned it. The `select!` in the serve loop kept a `watch` read guard across an await. The shutdown wait now drops the guard in its own block. Commit `fe0a19e`.
- **X-WP41-10: `Pool` string alignment dropped.** Go's `Pool` string does not reach any output, so nothing observable changes.
- **X-WP41-11: TLS not supported.** `serve` returns `Error::TlsNotSupported` when TLS is configured. Go accepts `--ssl-*`. See O-WP41-2.
- **X-WP41-12: step gauges.** Carried over from Go as described in X-WP41-5.

## Tests and TDD

- Worker tests: 17 `#[tokio::test]` functions cover Go's 16 suite methods and `TestWorker_Sync`. `TestWorker` in Go only runs the suite, so it has no separate port.

The harness unit tests (`set_key`, `flags`, `toml_string`, `go_duration`, the contract-keys test) were written in one pass with their implementation, and their first run was green. The `set_key` end-of-file case was fixed before the first run, and the tests cover it.

## Open items (O-WP41-n)

- **O-WP41-1: FP16 values in templates.** The rerankers and decision API receive embeddings as FP16 bit values, as the ported `ItemCache` stores them. Go renders its reranker and decision templates with gonja, and this port uses minijinja. Rendering numeric arrays may differ between the two. Not checked against Go output.
- **O-WP41-2: TLS.** The worker refuses TLS. The `--ssl-*` flags are accepted by the CLI, so this only matters for a TLS deployment. The fix is to wire `gorse_common::util::tls` into the connection and the HTTP server.
- **O-WP41-3: backend suites.** The workspace run in this container has 27 failures, all from missing environment variables (`MYSQL_URI`, `MARIADB_URI`, `POSTGRES_URI`, `MONGO_URI`, `REDIS_URI`, `QDRANT_URI`, `GCS_EMULATOR_ENDPOINT`, `S3_ENDPOINT`, `AZURE_STORAGE_CONNECTION_STRING`). None touches the worker. The integrator runs them on the merged head with the URIs set.
- **O-WP41-4: mixed-test coverage.** The mixed test covers the latest recommender only. Collaborative filtering, FM ranking and rerankers are compared in process, not across Go and Rust nodes.
- **O-WP41-5: no empty-list case in the mixed test.** Every user gets 28 rows, so the nil-versus-empty answer (X-WP41-8) rests on reading the code, not on a run.
- **O-WP41-6: comparison not mutation-checked.** The acceptance test passes. I did not run a deliberately wrong Rust output to show the test fails on a difference.
