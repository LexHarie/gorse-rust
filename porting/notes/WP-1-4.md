# WP-1-4 notes: util (math/rand, strconv, util, tls)

Provisional ids; the integrator renumbers them into `PORTING_NOTES.md` and
`PORTING.md`. The Rust modules are `crates/gorse-common/src/util.rs` (with
`util/rand.rs`, `util/rand/`, `util/random.rs`, `util/tls.rs`) and
`src/gostrconv/atof.rs`. The Go oracle data is in
`crates/gorse-common/tests/data/` and `src/util/rand/tables.rs`, written by
three tools from go1.27.0 (the toolchain `go.mod` selects at add21b5):

```
go run ./contracts/tools/randgolden \
  -tables-out crates/gorse-common/src/util/rand/tables.rs \
  -out crates/gorse-common/tests/data/rand_golden.json
go run ./contracts/tools/utilgolden -out crates/gorse-common/tests/data/util_golden.json
go run ./contracts/tools/tlsgolden \
  -dir crates/gorse-common/tests/data/tls \
  -out crates/gorse-common/tests/data/tls_golden.json
```

`randgolden` and `utilgolden` are reproducible (regenerating gives
byte-identical files). `tlsgolden` makes new random keys on every run, so it
rewrites every certificate; the verdicts must come out the same. `randgolden`
runs itself a second time with `GODEBUG=cpu.fma=off` to record Go's non-FMA
`math.Exp`, and fails if both runs agree.

The live check between Go and Rust peers, which is not part of `cargo test`:

```
cargo build --release -p gorse-common --example tls_peer
go run ./contracts/tools/tlsgolden -interop target/release/examples/tls_peer
```

These commands belong in the regeneration list of `contracts/README.md`
(not edited here).

## Plan corrections

- **C-WP4-1 TLS needs a patched `rustls`.** Go workers and servers dial the
  master with `util.NewClientCreds`, built on grpc's `advancedtls`, whose
  `ClientHandshake` uses the dial target `host:port` as the TLS server name
  (it does not strip the port), and Go's `crypto/tls` sends it as is. Stock
  `rustls` 0.23.46 aborts the handshake on such a name
  (`ServerNameMustContainOneHostName`), so a Rust master would refuse every
  Go client: unpatched, 34 of the 62 interop cases differ, every one that
  reaches a handshake. Ritchie chose the patch on 2026-10-18 (decision card
  "How should a Rust master accept Go workers' TLS connections?"):
  `third_party/rustls` is the published 0.23.46 with one change in
  `src/server/hs.rs`, so the server ignores a server name that is not a DNS
  name, as it already did for an IP address. It is wired in with
  `[patch.crates-io]` and kept out of the workspace with `exclude`.
  `third_party/`, not `vendor/`, because the Go toolchain gives a `vendor/`
  directory next to `go.mod` its own meaning. `GORSE.md` there says how to
  upgrade. `porting/crate-selection.md` had no row for TLS; one is added.
- **C-WP4-2 `aws-lc-rs`, not `ring`.** The certificates Gorse's own TestSSL
  makes (`madflojo/testcerts`) are P-521, which `ring` cannot verify.

## Decisions

- **D-WP4-1 Go's checks on the CA certificate.** `advancedtls` in
  `CertVerification` mode runs `x509.Verify` with the purpose's extended key
  usage and no host name. `webpki` keeps only the name and key of a trust
  anchor, so `util/tls.rs` runs Go's other checks in `webpki`'s path
  callback, on every chain `webpki` builds (a rejected chain makes it try the
  next, as Go tries other chains): the CA must be valid now, its extended key
  usage (if any) must include the purpose or `anyExtendedKeyUsage`, the
  number of intermediates must respect its `MaxPathLen`, and every issuer,
  the CA included, must pass Go's `CheckSignatureFrom` constraints (a v3
  certificate needs `BasicConstraints` with `cA`, and a `KeyUsage` with any
  bit set must include `keyCertSign`). A custom `ExtendedKeyUsageValidator`
  accepts `anyExtendedKeyUsage` on the leaf, as Go does and `webpki` does
  not. `x509-parser` reads the fields.
- **D-WP4-2 Verdicts, not error texts, for handshakes.** `tls_golden.json`
  records Go's error texts for reading; the tests compare whether each side
  built its credentials, whether the handshake and a ping/pong went through,
  which side rejected the other, and the ALPN protocol. Credential errors
  that Gorse surfaces at start-up match Go's text: `open <path>: <os error>`,
  `failed to append certificate`, `tls: failed to find any PEM data in
  certificate input` / `key input`, and `tls: ...` for a key that does not
  match its certificate.
- **D-WP4-3 Number parsing lives in `gostrconv`.** WP-1-4 first ported
  `Atoi`, `ParseInt`, `ParseUint` and `ParseFloat` under `util::strconv`.
  WP-1-9 and WP-1-14 have since merged `gostrconv` with `Quote`, `IsPrint` and
  the integer parsers (any base, Go's `(value, error)` shape), so WP-1-4 drops
  its copies and adds only `ParseFloat` as `gostrconv/atof.rs`, in the same
  shape (0 with a syntax error, the signed infinity with a range error). The
  WP-1-4 Go corpus (`util_golden.json`) now also checks `gostrconv`'s
  `atoi`, `parse_int` and `parse_uint` with bit size 0, including the value
  Go returns next to an error, and `quote` and `is_print` at every edge of
  Go's print table: all match.
- **D-WP4-4 `util::parse_float`, `parse_int` and `parse_uint` return a
  `Result`.** Go's `util.ParseFloat[T]` and friends also return a value next
  to an error; every Gorse caller (`common/datautil/datautil.go`,
  `storage/cache/redis.go`, `dataset/dataset.go`) returns the error without
  reading it. Inputs are bytes (`impl AsRef<[u8]>`), as in `gostrconv`.
- **D-WP4-5 Tables come from Go.** `rand/tables.rs` (`rngCooked`, the
  ziggurat tables of `normal.go` and `exp.go`) is written by `randgolden`
  from Go's own values. The decimal constants of Go's amd64 `math.Exp` and
  `math.Log` are kept as Go's text, and a test checks the bits Go's assembler
  gives them.
- **D-WP4-6 Go's top-level `rand` functions are not ported.** Since Go 1.20
  they draw from a randomly seeded runtime source and `rand.Seed` is a no-op,
  so nothing about them is reproducible.

## Quirks reproduced

- **Q-WP4-1 `Sample` and `SampleInt32` count excluded values outside the
  interval.** The "take everything" branch triggers when `n >= high - low -
  |exclude|`, with every excluded value counted, and then returns every
  allowed value, which can be more than `n`: `Sample(5, 50, 41, {6, 7, 100,
  -1})` returns 43 values (`common/util/random.go`). Covered by Go goldens
  either side of the threshold.
- **Q-WP4-2 `NormFloat64`, `ExpFloat64` and Go's `math.Exp` follow the
  CPU.** On amd64 Go's `math.Exp` uses FMA when the CPU has it and gives
  different bits without it; the Rust port detects FMA at run time the same
  way and has both paths checked against Go (`GODEBUG=cpu.fma=off` for the
  plain one). The ziggurat samplers only reach `Exp` and `Log` in their rare
  rejection branches. Go's amd64 `math.Log` does not normalise subnormal
  inputs; nor does the port.
- **Q-WP4-3 Go's `NaN` bits.** `ParseFloat("nan")` returns Go's
  `math.NaN()`, bits `0x7FF8000000000001`, not Rust's `f64::NAN`.
- **Q-WP4-4 No host name is checked on either side**
  (`advancedtls.CertVerification`): a certificate for another host is
  accepted.
- **Q-WP4-5 `h2` is offered as ALPN on both sides and enforced on neither.**
- **Q-WP4-6 A CA limited to server authentication works in a client's CA
  file and makes a server reject every client**: the server checks client
  certificates for client authentication all the way up to the CA.
- **Q-WP4-7 A client whose chain does not reach the server's CA**: the Go
  client sends no certificate (none matches the server's CA hints) and the
  Go server reports `client didn't provide a certificate`; a Rust client
  sends its certificate anyway and the server rejects the chain. The verdict,
  rejected by the server, is the same.
- **Q-WP4-8 `ParseInt` with bit size 1 drops a range error**
  (`ParseInt("-2", 10, 1)` is `-1, nil` in go1.27.0). Gorse never uses bit
  size 1; noted because `gostrconv::parse_int` (WP-1-14) has the same logic
  (by reading the code; its tests do not exercise that case).

## Evidence

- `util_tls_matches_go_on_every_case`: all 62 Go cases (TestSSL's three,
  server and client key pairs ×16 each, CA files ×5 each, broken files ×8
  each, a client without a certificate) give Go's verdict.
- Interop: 124 runs, 0 differ from Go to Go.
- `util_tls_server_ignores_a_host_and_port_server_name` fails against the
  unpatched `hs.rs` and passes with the patch.
- Mutation checks (one mutation at a time, the named test run in release
  mode): every mutation was caught: the `rngCooked` table, Exp's FMA path,
  Log's `Sqrt2/2` boundary, Go's NaN bits, ParseFloat's value on a range
  error, Sample's exclusion count, ALPN, CA validity, `anyExtendedKeyUsage`,
  issuer key usage, CA path length, an empty CA file, one byte of the rand
  golden and one verdict of the TLS golden.
