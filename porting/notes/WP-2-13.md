# WP-2-13 notes: schema conformance checker (provisional ids)

Crate `gorse-conformance`, module `schema` (`conformance/src/schema/`), tests in
`conformance/tests/schema.rs`. Tool change: `contracts/tools/schemadump` gains a
`-dump-only` mode (coordinator approval, 2026-10-28). Provisional ids: the
integrator renumbers them at the fold.

## Result

For SQLite, MySQL 8.0.46, PostgreSQL 10.0, MongoDB 6.0.28 and the meta store, each
Rust-initialised database is dumped by the Go tool (primary check) and by the Rust
mirror (second check). Both equal the Go-initialised dump and `contracts/schema/`.
Redis 8 agrees on `FT.INFO documents` after the normalisation in D-WP213-5. MariaDB
10.2.44 is compared with the Go-initialised dump, since it has no frozen file. No
store difference was found.

## Decisions

- **D-WP213-1 The Go tool dumps the Rust databases; the Rust mirror is a second
  check.** `schemadump`'s full run creates its own databases, so it cannot dump one
  that a Rust store made. The approved change is a `-dump-only` mode: `-dump-only
  <kind>` with `-target` (a file, a DSN with its database, or a URL), `-database`
  (PostgreSQL and MongoDB) and `-postgres-container` (PostgreSQL). It writes one dump
  to stdout and changes nothing. The kinds are `sqlite`, `mysql`, `postgres`,
  `mongodb` and `redis`. The full run's code is unchanged except that the Redis
  `FT.INFO` text moved into a helper with the same format. The Go tool's PostgreSQL
  dump reproduces `dump-schemas.sh` line by line. `schema::dump` (the Rust mirror)
  remains as a second check, so a fault shared by the Rust stores and a mirror of
  the Go format cannot hide a diff.

- **D-WP213-2 `pg_dump` runs inside the server container.** Both dumpers run
  `pg_dump -s` through `docker exec` in `POSTGRES_CONTAINER` (default
  `storage-postgres-1`), as `dump-schemas.sh` does. The host's `pg_dump` is 16 and
  would not match the server's 10.0 output.

- **D-WP213-3 Separate databases.** Go writes `gorse_schema_*` and Rust writes
  `gorse_rs_schema_*`, so neither build reads the other's database. Each test drops
  and creates its own databases first.

- **D-WP213-4 A missing backend fails, it does not skip.** Each test needs its URI
  (`MYSQL_URI`, `MARIADB_URI`, `POSTGRES_URI`, `MONGO_URI`, `REDIS_URI`) and fails
  without it, as `conformance/README.md` requires. The Go tests skip instead.
  SQLite needs no server.

- **D-WP213-5 Run-dependent values and read counts.**
  1. `FT.INFO`'s `total_indexing_time` is wall-clock and is replaced by
     `<run-dependent>` on both sides (`schema::normalise_ft_info`). It is the only
     normalisation.
  2. Every `FT.INFO` call increments `number_of_uses`. So each dump reads a
     freshly built index exactly once: the Go tool reads first, the index is
     rebuilt, and the Rust mirror reads second. The contract's `number_of_uses 1` is
     the first read after `Init`.

- **D-WP213-6 MariaDB 10.2 has no frozen dump.** `contracts/schema` holds MySQL 8.0
  only. `schema_mariadb` compares the Go-initialised dump with both dumps of the
  Rust database. The MariaDB dump differs from the MySQL one in three ways, and each
  is the server, not the port: the server version line, `DEFAULT '0'` shown as
  `DEFAULT 0` for `double`, `labels` as `longtext` instead of `json`, and the
  multi-valued index `idx_collection_subset_categories` missing on MariaDB.

- **D-WP213-7 Samples are not in the schema check.** The full run also writes
  `samples/*.json` (rows and encodings). WP-2-13 compares the schema files only, as
  its brief says.

## Proof that the existing outputs are unchanged

- Baseline: the full run of the tool before the change, with all four backends.
  After: the full run of the changed tool. Every schema file is byte-identical,
  except `cache/redis.ft-info.txt`, where one token differs: `total_indexing_time`
  0.07176 against 0.061003 (wall-clock).
- The sample files differ only in run-dependent values: MongoDB `_id` (ObjectId)
  and `update_at`, and the MySQL, PostgreSQL and SQLite `update_at` timestamps.
- The `-dump-only` mode reproduces the full run's files on the Go-created databases:
  MySQL `gorse_schema_data` and `gorse_schema_cache`, MongoDB both databases, and
  the three PostgreSQL databases against `contracts/schema`. All are byte-identical.
- The primary check is not vacuous: a column added to a Rust-initialised MySQL table
  changes the Go tool's dump, and the diff shows the new column.

## Open

- **O-WP213-1 Samples and the Redis key layout.** The Go `samples/*.json` files and
  the Redis key listing (`samples/cache.redis.json`) are not compared. The
  coordinator's "key layout where applicable" covers `FT.INFO`.
- **O-WP213-2 Other servers.** Only the Go and Rust builds at the pinned commit were
  run. Kvrocks and the six-node Redis cluster (the Go CI's compatibility job) are
  not in this WP.

## Q-229 (schema equality)

Closed. The tables the Rust cache and data stores create equal
`contracts/schema/{mysql,postgres,sqlite}.sql` on MySQL 8.0.46, PostgreSQL 10.0 and
SQLite, and the search variants equal the Go reconcile output (`schema_mysql`,
`schema_postgres`, `schema_sqlite`). The Go tool's dump-only mode and the Rust mirror
both agree with the contract.
