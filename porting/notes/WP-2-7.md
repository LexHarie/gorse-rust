# WP-2-7: MongoDB cache store

Ports: `storage/cache/mongodb.go`, `storage/cache/mongodb_test.go` @ add21b5.
Rust: `crates/gorse-storage/src/cache/mongodb.rs`, behind feature `mongodb`.
Acceptance: `MONGO_URI=mongodb://root:password@127.0.0.1:27017/ cargo test -p gorse-storage --features mongodb cache::mongodb`.
Integrator: merge commit `9e3aa92` (the approved trait fix) before this WP.

## Decisions

- **D-WP27-1 The driver is `mongodb` 3.9.1.** It is the latest stable release on
  2026-10-28 (`cargo info mongodb`) and Apache-2.0, as `porting/crate-selection.md`
  already says. It is an optional dependency of `gorse-storage`, behind the
  `mongodb` feature, so a build with no MongoDB store does not link it. The
  driver's default BSON is `bson` 2.15.

- **D-WP27-2 `MongoDB::open` is `async`, and the registry does not hold it.**
  Go's creator calls `mongo.Connect`, which is lazy. The Rust driver's
  `ClientOptions::parse` is `async`, and `Client::with_options` spawns tasks on
  the runtime. So `MongoDB::open(path, table_prefix)` is an async function. It
  is not registered in `cache::Registry`, whose `Creator` is a sync `fn`. See
  O-WP27-1.

- **D-WP27-3 The callbacks of `scan` and `scan_scores` take any lifetime.** The
  trait bounds are `for<'a> FnMut(&'a str)` (and `for<'a, 'b, 'c>` for
  `scan_scores`), which the approved fix in `9e3aa92` sets. `async-trait`
  rewrites the elided lifetime inside `FnMut(&str)` into a named lifetime, so a
  backend cannot call the callback with a string it borrowed from a row
  (rustc E0597). Redis (WP-2-5) and SQL (WP-2-6) take the same commit.

- **D-WP27-4 Each write is its own round trip.** The driver's `bulk_write` needs
  MongoDB 8.0, and the suite runs on 6.0.28. Each write is an
  `update_one(...).upsert(true)`, in order, and the first error stops the batch.
  That is what Go's ordered bulk write does on the server.

- **D-WP27-5 Collections and indexes match Go.** Collections are
  `<prefix>values`, `<prefix>documents` and `<prefix>time_series_points`. `init`
  creates the values collection, then the two indexes on documents and the one
  on points, with the keys Go uses. On mongo:6 (6.0.28), `getIndexes()` on the
  Go-created and the Rust-created `gorse_cache_test` lists the same index names:
  `collection_1_subset_1_id_1`, `collection_1_subset_1_categories_1_is_hidden_1_score_-1`
  and `name_1_timestamp_1`.

## Quirks reproduced

- **Q-WP27-1 An empty write of time series points is an error.** `AddTimeSeriesPoints`
  with no points returns "must provide at least one element in input slice" (the
  driver's `ErrEmptySlice`). The other writes return nil on an empty list.
  Observed with the Go oracle on 2026-10-28.

- **Q-WP27-2 `Purge` leaves the time series points.** Go purges the values and the
  documents collections only. Reproduced.

- **Q-WP27-3 Scan loops swallow cursor errors.** `Scan`, `SearchScores` and
  `ScanScores` stop at a cursor error without returning it, because Go never
  calls `cursor.Err()` there. `GetTimeSeriesPoints` does check it, so the port
  returns that error. Reproduced.

- **Q-WP27-4 Times are stored in milliseconds, with Go's formula.** Go writes
  `t.Unix()*1e3 + t.Nanosecond()/1e6`. Oracle: `time.Unix(-2, 999999999)` is
  stored as -1001 ms and read back as `1969-12-31 23:59:58.999 +0000 UTC`.
  Whole-nanosecond truncation would give 23:59:59.000, so the port uses Go's
  formula (`to_datetime`). Positive times behave the same either way.

- **Q-WP27-5 `IsHidden` is always false when read.** Go's BSON decoder reads the
  key `ishidden`, which the store never writes. The search filters hidden
  documents, so reading `is_hidden` gives the same result, and the port sets
  false directly. No observable difference.

- **Q-WP27-6 Go sends one `$set` per patched field.** `UpdateScores` with two or
  more fields emits duplicate `$set` keys. The server applies them all: the
  oracle's patch of `is_hidden`, `score` and `categories` changed all three. The
  port sends one `$set` with the same fields, so the result is the same.

- **Q-WP27-7 A negative `begin` is refused by the server.** The driver's skip is
  unsigned, so the port refuses it itself, with the server's text:
  `(Location51024) BSON field 'skip' value must be >= 0, actual value '-1'`
  (oracle, MongoDB 6.0.28). `limit` of 0 is unlimited on the server, as in Go;
  the oracle confirmed it.

## Deviations

- **X-WP27-1 `connect=direct` is read as `directConnection=true`.** Go's
  connection-string parser takes the legacy `connect` option. The Rust driver
  rejects it ("connect is an invalid option"). The suite's URI and the Gorse
  configs carry it. `connect=automatic` is the default, so it is dropped. Other
  options pass through unchanged. `driver_uri` does this.

- **X-WP27-2 A nil slice of categories is stored as an empty array.** Go writes a
  nil `Categories` as BSON null. `Score.categories` is a `Vec`, which has no nil,
  so the port writes `[]`. Both read back as no categories. Go's null value is
  still read as no categories.

- **X-WP27-3 The context is checked on entry and between documents.** Per D-122:
  `ctx.err()` before each call, and before each document in `scan_scores`. Go's
  driver also cancels an operation under way. Here an operation under way runs
  until the server answers or the driver times out. Dropping the future cancels
  it.

- **X-WP27-4 No OpenTelemetry command monitor.** Go sets
  `otelmongo.NewMonitor()` on the client. The port has no command monitor. Spans
  belong with the tracing work (O-17), in the server and master WPs.

- **X-WP27-5 Each write is its own round trip.** Same results, more round trips
  (D-WP27-4).

## Open

- **O-WP27-1 Opening the store in a node.** `cache::Registry` takes a sync
  `Creator`, and the MongoDB open needs the async driver (D-WP27-2). Options:
  the node calls `MongoDB::open` itself for `mongodb://` and `mongodb+srv://`
  paths, or the `Creator` type becomes async (a shared change to WP-2-4). Phase 4
  decides. The suite does not need either.

- **O-WP27-2 The test without `MONGO_URI`.** The test returns early and reports
  `ok`, as Go's `t.Skip` does. The acceptance run sets `MONGO_URI`, so it runs
  every suite case.

- **O-WP27-3 MongoDB versions tested.** Only 6.0.28 (the `mongo:6` image, the
  version PORTING.md pins) is run here. The root `docker-compose.yml` has a
  commented `mongo:4.0`, and the Go CI's compatibility job is not run here. The
  driver's minimum server version is not checked.

- **O-WP27-4 `gosort` copy.** This store does not sort in Rust (MongoDB sorts
  on the server). The duplicate `pdqsort` in `cache/gosort.rs` is WP-2-4's and
  is not changed here (O-27, owned by the cache core).

## Evidence

- Shared suite: `MONGO_URI=mongodb://root:password@127.0.0.1:27017/ cargo test -p gorse-storage --features mongodb cache::mongodb` passes on MongoDB 6.0.28 (`test cache::mongodb::tests::mongo ... ok`).
- Go oracle on the same server: `go test ./storage/cache -run TestMongo -v` passes all 10 suite cases (log kept outside the repo).
- Cross-check, both ways (temporary tests and probes, not committed):
  - Go wrote a score document with categories null and a 1999999 ns timestamp. The Rust store read it back with the same values as Go: categories `[]`, timestamp `1969-12-31 23:59:58.999`, and the scan timestamps as Go reports them.
  - The Rust store wrote scores, a patch, time series points and a value. Go read them back: `ts=2023-01-01 00:00:00.001` for the 1999999 ns score, `2023-01-01 00:00:00` for the 500 ns one, points `3.5` and `4.5`, and value `"v"`.
- Gate on the branch head (default features, plus clippy with `--features mongodb`): fmt exit 0; clippy `-D warnings` exit 0 for the workspace and for gorse-storage with `mongodb`; `cargo test --workspace --no-fail-fast` exit 0 (844 passed, 0 failed, 12 ignored); `RUSTDOCFLAGS='-D warnings' cargo doc --workspace --no-deps` exit 0; `go vet ./...` in `contracts/tools` exit 0.
