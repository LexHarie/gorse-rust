## O-76: nil or empty per route

Go's `encoding/json` writes a nil slice as `null` and an empty one as `[]`.
Each answer below comes from running the Go server in-process on empty stores
with the default configuration (probe, 2026-10-29), from the Go test
expectations, or from the Go source as marked.

| Route | Empty store (Go probe) | Other evidence |
| --- | --- | --- |
| `GET /api/items` | `{"Cursor": "", "Items": []}` | test `TestItems`, `TestFeedback` |
| `GET /api/users` | `{"Cursor": "", "Users": []}` | test `TestUsers` |
| `GET /api/feedback` | `{"Cursor": "", "Feedback": []}` | test `TestFeedback` |
| `GET /api/latest`, `/api/latest/{category}` | `[]` | test `TestItems` (`/api/latest/*` after deletes gives `[]`) |
| `GET /api/recommend/{user-id}[/{category}]` | `[]` | probe; test `TestGetRecommends` (`offset=10000` gives `[]`) |
| `GET /api/non-personalized/{name}` | `[]` (also past the end) | probe |
| `GET /api/collaborative-filtering/{user-id}[/{category}]` | 404 when disabled | probe |
| `GET /api/user/{user-id}/feedback`, `/api/item/{item-id}/feedback` | `[]` | probe; test `TestFeedback` |
| `GET /api/user/{user-id}/feedback/{type}`, `/api/item/{item-id}/feedback/{type}` | `[]` | probe; test `TestFeedback` |
| `GET /api/feedback/{user-id}/{item-id}` | `[]` | probe; test `TestDeleteFeedback` |
| `GET /api/feedback/{type}/{user-id}/{item-id}` | `{}` (typed, absent) | probe; test `TestDeleteFeedback` |
| `GET /api/item/{item-id}/neighbors[/{category}]`, `/api/item-to-item/{name}/{item-id}` | 404 when not configured | probe; item-to-item `offset` past the end gives `null` (source: `server/rest.go` 860–872, a nil `[]cache.Score` when `offset >= len`) |
| `GET /api/user/{user-id}/neighbors`, `/api/user-to-user/{name}/{user-id}` | 404 when not configured | `offset` past the end gives `null` (source: `server/rest.go` 906–915) |
| `POST /api/session/recommend[/{category}]` | 404 when item-to-item is off | `offset` past the end gives `null` (test `TestSessionRecommend`, `[]cache.Score(nil)`) |

Rust: every list is a `Vec`, so an empty store answers `[]`. The two routes
that answer `null` past the end (item-to-item and user-to-user neighbours, and
the session recommendation) use `Option<Vec<_>>` and return `None` when the
offset is past the end.

Not yet confirmed by a live Go answer: item-to-item and user-to-user `offset`
past the end (the source says `null`). The conformance test will check it.

## Deviations (X-WP42-n)

1. **TLS to the master is not ported.** `Server::serve` refuses a configured
   TLS with a clear error. WP-4-3 ports it with `gorse_common::util::tls`.
2. **OpenTelemetry tracing is not applied** in `Sync`. Go's `Sync` sets up the
   tracer from the master's config; the Rust sync does not yet.
3. **`/debug/pprof` and the Swagger UI at `/apidocs/` are not served.**
   `/apidocs.json` is served, from the frozen contract file.
4. **go-restful's CORS container filter is not implemented.** The `Ok` helper
   still sets `Access-Control-Allow-Origin: *` on success responses, as Go does.
5. **`RemoteAddr` is always empty** in request events. The router is served
   without `ConnectInfo`. Go's test expects it empty under `apitest` too.
6. **The REST API histogram has a help text.** Go registers it with an empty
   help text; the Rust `prometheus` crate rejects an empty one. The `/metrics`
   `# HELP` line therefore differs.
7. **Floats in exponent form** are written by `serde_json` (`ryu`), not by Go's
   `strconv`. Values are equal; the text can differ for very large or very
   small numbers.
8. **Go's JSON decoder matches keys case-insensitively** and serde does not, so
   a request with `"itemid"` for `ItemId` is refused here and accepted by Go.
   Not tested; a real divergence for clients that send other cases.
9. **Trailing slashes are trimmed before routing** (`rest.rs`,
   `trim_trailing_slash`). go-restful routes `/api/latest/` as `/api/latest`
   and `/api/item/x/neighbors` as `/api/item/x/neighbors/`. The routes are
   registered without the slash.
10. **Labels in request bodies:** Go decodes requests with `UseNumber`, so
    numbers in labels are `json.Number`s. The storage decoder reads numbers as
    `float64`, so `response::validate_request_labels` converts them to
    `Labels::Number` before validation. A whole number's text is exact; a
    fraction keeps the shortest text that reads back (`2.50` is written `2.5`).
11. **Request bytes are the bytes the handler reads**, counted by wrapping the
    body, as Go's `CountingReadCloser` does. The response bytes are the body's
    exact size.
12. **Not-found text includes the name** (`item 6 not found`), which Go's
    storage layer adds to `ErrNotFound`. The Rust storage error does not carry
    the name, so the server adds it.
13. **`serde_json` parses floats exactly** (`float_roundtrip` feature in
    `gorse-server`). Without it a score can differ by one ulp from Go's
    `strconv`. The workspace `serde_json` does not enable this, and that is a
    shared-crate decision (see Q-WP42-2).

## Decisions (D-WP42-n)

1. **Request context is `Context::background()` per request.** Go passes the
   request context. axum cancels a handler when its future is dropped, which
   covers the common case. Propagating the request context is not needed for
   the tests.
2. **Request events are emitted on `spawn_blocking`,** as Go emits them on a
   goroutine, so the response does not wait for the handler.
3. **Tests open fresh stores per test,** where Go's suite shares them and
   purges them in `SetupTest`. Each test sees only its own rows.
4. **The router's fallback trims the trailing slash** (deviation 9), so the
   API routes stay as Go's route table writes them, minus the slash.

## Questions (Q-WP42-n)

1. **Q-WP42-1:** Does the mixed-server conformance run need the item-to-item
   and user-to-user `offset` past the end checked live? Yes, once WP-4-1 lands.
2. **Q-WP42-2:** Should the workspace `serde_json` enable `float_roundtrip`?
   It fixes a one-ulp difference for the item-to-item test (the Go value is
   the nearest double to `1/101`). That is a shared-crate change, so it needs
   the coordinator's approval.
3. **Q-WP42-3:** Labels that are floats in requests, such as `2.50`. Go keeps
   the text. The Rust text is `2.5`. Acceptable, or should the request decoder
   keep the number text? It would need the decoder to see the text, which is a
   storage-crate change.
