## Status

The test runs both clusters, sends all 107 requests to each, and compares them. The last run
(golden-run5) gave 93 routes identical, 28 explained differences and 9 unexplained differences.
The test fails on the 9. They are port bugs, listed under "Open diffs" below. The test is not
skipped or weakened to pass them.

Rulings applied on this branch: the score tolerance is D-234 (`|rust - go| <= 1e-6 * max(|go|, 1)`), and
the size in the B3 text is masked as D-299 says (see B3 below). On this head, run 10 (1309.81 s) gives
107 routes, 93 identical, 28 explained (25 of them `X-WP51-1`) and 9 unexplained. The B3 lines show `<N>` on
both sides and the limit 4194304 exact. The lines are in `porting/notes/wp-5-1-evidence/run10-rest-golden.txt`. WP-5-1 stays blocked until B1, B2, B3 and B4
are fixed and O-92 and O-93 are merged (court, D-299).

## Harness decisions (D-WP51-1)

1. The two clusters are seeded as `client/setup-test.sh` does: the config is `client/config.toml`, the
   MovieLens 100k dump is restored through `/api/restore` (counts 943, 1,682, 100,000), the master
   restarts, and the master's training is waited for. The dump is read from
   `/mnt/project-files/datasets/ml-100k.bin.gz` (or `GORSE_ML_100K_DUMP`), as `tests/mixed_cluster.rs`
   does. `scripts/setup-datasets.sh` places only zips.
2. The recommendation wait ends when the set of users with a `recommend_update_time` has stayed the
   same for 120 s (two worker intervals). It does not wait for every user. See Q-WP51-2. The
   `Cluster::wait_for` limit of 120 s is too short for the first pass (about 140 s for 943 users), so
   the test has its own 900 s deadline.
3. Each request goes to the node its table describes: master rows to the master, server rows to the
   server. Reads go first, then writes, each in table order. Both clusters get the same order.

## Quirks reproduced (Q-WP51-n)

1. **Q-WP51-1: five rows omit a path placeholder.** The parameter cells of
   `GET /api/dashboard/item-to-item/{name}/{item-id}`, `GET /api/dashboard/user-to-user/{name}/{user-id}`,
   `GET /api/dashboard/non-personalized/{name}` (master) and `GET /api/non-personalized/{name}` (master and
   server) do not name `name`, so the OpenAPI document and the table have no parameter for it. The Go
   handlers read it from the path. The test fills it from the same sample as a listed path parameter, and
   allows only the four paths in `UNLISTED_PATH_PARAMS`. Any other placeholder gap fails the test.
2. **Q-WP51-2: a cold-start user gets no recommendation update time.** `worker/pipeline.go` returns
   before the write for a user with no positive feedback (`IsColdStart`). User 685 of the dump is one. So
   no run ever has an update time for every user, and the seed wait is on stability (D-WP51-1 item 2).

## Explained differences (X-WP51-n)

1. **X-WP51-1: item-to-item scores differ by up to 7.5e-7 relative.** The affected routes are
   `GET /api/dashboard/item-to-item/{name}/{item-id}`, `GET /api/item-to-item/{name}/{item-id}`,
   `GET /api/item/{item-id}/neighbors/` (master), and `POST /api/session/recommend` (master and server).
   Go computes the scores from float32 vectors with its kernels, and the Rust port with the `cc` kernels
   of `gorse-common`. Each score is covered under the rule of D-234: `|rust - go| <= 1e-6 * max(|go|, 1)`.
   The entries are in `EXPLAINED`, with that tolerance, so a larger difference fails the test.

   Evidence for the 1e-6 value:
   - The value and the Go oracle. `conformance/tests/item_to_item_oracle.rs:364` sets
     `SCORE_TOLERANCE = 1e-6`. That test runs `contracts/tools/item2itemgolden` with `go run` on 40
     seeded cases. The court accepted it in PORTING.md D-234 (WP-3-5, head `65e6308`): "their scores agree
     within 1e-6 of `max(|score|, 1)`". The same constant, at `conformance/tests/recommend_oracle.rs:47`,
     was accepted in D-236 (WP-3-7, largest gap 4.77e-7).
   - The measured gap. Run 5 (head 17184b5, 1287.87 s) printed 25 `X-WP51-1` score lines. The largest
     relative gap is 7.48e-7 (`|x - y| / max(|x|, |y|)`), and the largest absolute gap is 3.75e-7. The
     lines are in `porting/notes/wp-5-1-evidence/run5-rest-golden.txt`.
   - The rule applied. The court ruled on the rule for this WP (head 1276f6e, relayed 2026-11-02 03:06Z):
     the accepted rule of D-234 is `|rust - go| <= 1e-6 * max(|go|, 1)`. `rest_golden.rs` uses it in
     `within()`, and the unit test `scores_are_covered_by_the_accepted_rule` checks it on both sides of
     the bound. Under this rule the 25 score lines of run 5 are covered, since the largest absolute gap
     is 3.75e-7 and the bound is 1e-6 for scores below 1. The previous check, a relative gap with no floor,
     was stricter for scores below 1 and is removed. Run 8 is the run on the new rule (1322.00 s). It gives
     the same counts as run 5: 107 routes, 93 identical, 28 explained (all 25 `X-WP51-1` lines among them),
     9 unexplained. Its lines are in `porting/notes/wp-5-1-evidence/run8-rest-golden.txt`. Runs 6 and 7
     stopped while building the Rust nodes, because the disk was full. They did not reach the comparison.
2. **X-WP51-2: the node's `Version` string.** `GET /api/dashboard/cluster` shows `unknown-version` for the
   Go nodes, which are built without the version ldflag, and `0.0.0` for the Rust nodes, which show their
   crate version. The field is build metadata, so any value is covered.
3. **X-WP51-3: a task's `Count`.** `GET /api/dashboard/tasks` reports a worker task's progress when the
   list is read. Each cluster's worker runs its pass on its own clock, so the counts differ (for example 888
   and 337 in one run, 908 and 321 in another). Any value of `Count` is covered.

The node and worker ids in the cluster and task lists are 32-digit hex ids. N2 of the test normalises
them as generated ids, so they are not explained diffs.

## Open diffs (port bugs, not explained; owners to be assigned by the court)

Each of these fails the test. The fix belongs to the owning WP, and no production code changes here.

1. **B1 (master, `POST /api/dashboard/config`, no body, no Content-Type): Go 415, Rust 400 `EOF`.** Go's
   master web service declares `Consumes(restful.MIME_JSON)` (`master/rest.go:84`). go-restful refuses a
   POST or PUT whose Content-Type does not match with `415 Unsupported Media Type`, before the handler runs.
   The Rust master (`crates/gorse-master/src/rest/config.rs`, `post_config`) takes the raw body and has no such
   check, so it reaches `posted_map` and answers `EOF`. The Rust server node has no check either, and it
   agrees with Go's server node, which has no `Consumes`.
2. **B2 (master, `PUT /api/item/{item-id}/category/{category}`, no body): Go 415, Rust 500 `not found`.**
   Same cause as B1, on the master only. The Rust 500 comes from an earlier write in the same run: the
   master's `DELETE /api/item/1` runs first, so `get_item` finds nothing. Go answers 415 before it gets that
   far. Once B1's check is in place, the Rust answer should be 415 too.
3. **B3 (server, four GET routes that read through the master): the gRPC error text.** Go's server answers
   `rpc error: code = ResourceExhausted desc = grpc: received message larger than max (...)`. The Rust
   server answers `rpc error: code = OutOfRange desc = Error, decoded message length too large: found ...`.
   Both fail with a gRPC message-size error on the same request, so the status and the text differ. The
   text must match Go exactly (coordinator ruling, 2026-10-28). The routes are `GET /api/item-to-item/{name}/{item-id}`,
   `GET /api/item/{item-id}/neighbors/`, `GET /api/item/{item-id}/neighbors/{category}` and `GET /api/latest`.
   The owner is the Rust proxy client (WP-2-12 / WP-4-2).

   **The size in the B3 text (D-299, court ruling 2026-11-02 05:57Z, harmonised with the coordinator).**
   The golden masks only the size N of a too-large message, written `<N>`, on each side whose text matches
   a too-large error: Go's `(N vs. M)` and tonic's `found N bytes, the limit is: M bytes`. The limit M and the
   rest of the text stay exact. N must exceed M on each side, or the test fails. The code is in
   `mask_message_size` in `rest_golden.rs`, with the unit tests `only_the_size_of_a_too_large_message_is_masked`
   and `a_too_large_message_must_exceed_its_limit`. The mask does not hide B3: the codes (`ResourceExhausted`
   against `OutOfRange`) and the wording still differ, so these rows stay unexplained until the port matches Go.

   Why N is masked (O-91 probe, `porting/evidence/o91/README.md` on `claude/project-thread-4aex1f`): Go's N
   changes between runs of the same code, by 122 and 64 bytes. The only size-varying field is `update_at`, the
   wall-clock time of the restore, whose nanosecond varint is 4 or 5 bytes depending on the sub-second phase.
   Rust's N is the same in both runs. The same probe finds two byte differences that the mask does not touch,
   and that are not size-related: the float digits in `labels` (O-92) and Go's `-0.0` score, which Rust omits
   (O-93). The court lists both as blockers for WP-5-1. While B3 is open these routes return the error, not the
   items, so the golden does not compare those bytes yet.
4. **B4 (master, `GET /api/dashboard/recommend/{user-id}/{recommender}`, `collaborative`, user 1): Go
   returns 20 items, Rust returns `[]`.** Go and Rust both read `CollaborativeFiltering` for the user and
   its digest, and the golden's `/api/collaborative-filtering/1` route matches Go, so the missing piece is
   not the list itself. Not yet traced. Owner WP-4-4 (master REST), pending a trace of the Rust master's
   `recommend_sequential` for the `collaborative` source.
