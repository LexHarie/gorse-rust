## What the test does

- `conformance/tests/metrics.rs`, 13 tests, none ignored: 11 gate tests and 2 one-job tests
  (`ml_100k_bpr_one_job`, `criteo_afm_one_job`, see Results).
  - Gate 2, the replay (1e-5, D-195): `replay_cf_bpr_and_als_match_go` and `replay_ctr_afm_matches_go`
    run `contracts/tools/modelreplay` live into a temporary directory (with `GODEBUG=randautoseed=0`
    for ctr, as `ctr_replay.rs` does), then fit the Rust models for every epoch count and compare the
    metrics (and, for cf, the final factors). The committed goldens are checked against live Go by
    `cf_golden.rs` and `ctr_replay.rs`.
  - Gate 1, the datasets (D-195): one test per Go model test that loads a built-in dataset, plus the
    commented-out pinterest-20 tests and ml-100k. Each test runs the Go oracle
    `conformance/oracle/metrics` itself, then fits Rust on the same file.
- `conformance/oracle/metrics/main.go`: the Go side. It fits one configuration with the parameters of
  the Go test that uses the dataset, with `SetJobs(runtime.NumCPU())`, and writes the metrics as JSON.
  Its output for ctr includes the marshal round trip.
- `conformance/Cargo.toml`: two dev-dependencies, `gorse-model` and `gorse-model-core`.

## Deviations and choices (for the court)

- D-195 bands: NDCG and accuracy are checked against the value the Go test asserts, with the Go test's
  own delta. Precision, recall and AUC, which the Go tests do not assert, are checked against a Go run of
  the same configuration on the same file, within 0.01 (`benchDelta` and `classificationDelta`).
- Pinterest-20 (`model/cf/model_test.go`, commented out in Go): the value the commented code asserts is
  used as the NDCG reference (0.53 for BPR, 0.52 for ALS), within 0.01. Go does not run these tests.
- ml-100k: no Go test uses it. Its reference is a Go run of the ml-1m configuration (BPR and ALS).
- ml-tag: Go skips the test (`t.Skip`). It runs here, so no check is skipped.
- The ctr clone (marshal round trip) is checked where the Go test checks it (frappe, criteo).
- Parallel fits are not deterministic on either side: Go runs `SetJobs(NumCPU)`, and Rust runs at
  `available_parallelism()` jobs (Hogwild-style BPR). The NumCPU comparisons can therefore drift past the
  band. The one-job tests run both sides at one job and match exactly. See Results, needs-decision.
- FM initialisation: Go draws it from its process-global random source, which Go seeds at random. The
  oracle runs with `GODEBUG=randautoseed=0`, which pins Go's seed to 1, and the Rust side calls
  `Afm::set_init_seed(1)` (`INIT_SEED` in `metrics.rs`). Before the pin, two single-job Go criteo runs gave
  0.765 and 0.775, so the two sides never shared an initialisation.
- criteo: the archive holds a 200-row train and a 200-row test sample (O-1), not the full set. The Go
  test's 0.77 is applied to this sample, so the accuracy check is not evidence of parity with Go's
  full-data number. The Go-run comparison is the stronger check here.

### Needs-decision (court and coordinator)

The 0.01 band cannot be met reliably for parallel BPR recall. ml-100k BPR failed in two of five
repetitions, and ml-1m BPR recall sat at 9.1e-3 in the seeded run. Both sides move, so the Go reference is
not a fixed target at NumCPU jobs. No tolerance and no model was changed. Options:

- (a) Keep the NumCPU tests as they are. Their failures are noise, not a regression signal, so this is not
  recommended.
- (b) Gate BPR on single-job runs, which match Go exactly, and keep the NumCPU runs as output. This changes
  which runs count toward the gate, so it needs the court's ruling. Extending it to ml-1m and pinterest BPR
  is a short follow-up.
- (c) A measured, wider band for parallel BPR recall. This changes D-195 and needs coordinator approval.

The recommendation is (b). Option (c) needs coordinator approval.
