## What the test does

- `conformance/tests/metrics.rs`, 15 tests, none ignored: 11 gate tests and 4 one-job tests (see Results).
  The one-job tests are `ml_100k_bpr_one_job`, `ml_1m_bpr_one_job`, `pinterest_20_bpr_one_job` and `criteo_afm_one_job`.
  - Gate 2, the replay (1e-5, D-195): `replay_cf_bpr_and_als_match_go` and `replay_ctr_afm_matches_go`
    run `contracts/tools/modelreplay` live into a temporary directory (with `GODEBUG=randautoseed=0`
    for ctr, as `ctr_replay.rs` does), then fit the Rust models for every epoch count and compare the
    metrics (and, for cf, the final factors). The committed goldens are checked against live Go by
    `cf_golden.rs` and `ctr_replay.rs`.
  - Gate 1, the datasets (D-195): one test per Go model test that loads a built-in dataset, plus the
    commented-out pinterest-20 tests and ml-100k. Each test runs the Go oracle
    `conformance/oracle/metrics` itself, then fits Rust on the same file.
- `conformance/oracle/metrics/main.go`: the Go side. It fits one configuration with the parameters of
  the Go test that uses the dataset, with `SetJobs(runtime.NumCPU())`, and writes the metrics as JSON.
  Its output for ctr includes the marshal round trip.
- `conformance/Cargo.toml`: two dev-dependencies, `gorse-model` and `gorse-model-core`.

## Deviations and choices (for the court)

- D-195 bands: NDCG and accuracy are checked against the value the Go test asserts, with the Go test's
  own delta. Precision, recall and AUC, which the Go tests do not assert, are checked against a Go run of
  the same configuration on the same file, within 0.01 (`benchDelta` and `classificationDelta`).
- Pinterest-20 (`model/cf/model_test.go`, commented out in Go): the value the commented code asserts is
  used as the NDCG reference (0.53 for BPR, 0.52 for ALS), within 0.01. Go does not run these tests.
- ml-100k: no Go test uses it. Its reference is a Go run of the ml-1m configuration (BPR and ALS).
- ml-tag: Go skips the test (`t.Skip`). It runs here, so no check is skipped.
- The ctr clone (marshal round trip) is checked where the Go test checks it (frappe, criteo).
- Parallel fits (more than one job): Go's updates run without a lock, so Go's order follows the scheduler
  and Go's runs differ from each other (Q-269). Rust's BPR at more than one job is deterministic since
  X-253: shards run in rounds and merge in a fixed order. The NumCPU BPR check is therefore against the
  single-job Go run, not against one parallel Go run. See "Parallel BPR: X-253 and Q-269" below.
- FM initialisation: Go draws it from its process-global random source, which Go seeds at random. The
  oracle runs with `GODEBUG=randautoseed=0`, which pins Go's seed to 1, and the Rust side calls
  `Afm::set_init_seed(1)` (`INIT_SEED` in `metrics.rs`). Before the pin, two single-job Go criteo runs gave
  0.765 and 0.775, so the two sides never shared an initialisation.
- criteo: the archive holds a 200-row train and a 200-row test sample (O-1), not the full set. The Go
  test's 0.77 is applied to this sample, so the accuracy check is not evidence of parity with Go's
  full-data number. The Go-run comparison is the stronger check here.

## Parallel BPR: X-253 and Q-269

Q-269 (Go quirk): Go's parallel BPR (`SetJobs(NumCPU)`, updates without a lock) is not reproducible. Over 24
Go runs on this container, the recall of ml-100k BPR at four jobs spread from 0.7582 to 0.7805, and the
single-job recall is 0.7677625. Go misses the 0.01 band around its own mean in some runs. So this is Go's
own spread, not a Rust bug. Raw values: `porting/notes/wp-3-8-parallel-runs/go-numcpu-runs.txt` and
`go-final-head-runs.txt`.

Rust before the fix: each update took one lock, so the order of updates and the per-worker generators
followed thread scheduling. The Rust NumCPU runs drifted too: `rust-before-fix-runs.txt`.

X-253 (deviation): Rust's parallel BPR is more stable than Go's. Ritchie approved this on 2026-10-30. His
question, verbatim: "would it be okay if we fix Rust, and not necessarily follow Go for BPR? like it doesn't
miss in 12 runs". His answer: "yes". The coordinator relayed both.

The change is in `crates/gorse-model/src/cf/model.rs`, in `bpr_epoch_sharded`:

- One job (`jobs <= 1`) is unchanged. It uses one generator in Go's order, so the one-job tests and the
  replay still agree exactly with Go.
- More jobs: each epoch's updates are cut into `jobs` contiguous shards, the first `steps % jobs` one
  update longer. The shards run in rounds of 256 updates. In each round every shard runs its updates on
  its own copy of the factors, with its own generator (seeded in order from the model generator, as
  before). The copies' changes are then added to the round's starting factors in shard order. The shards
  share nothing during a round, so the result depends on the split, the round length and the generators,
  not on thread scheduling.
- The model file format and every contract are unchanged.

Rejected variant: one shard per job per epoch, with the changes merged once per epoch. ml-1m BPR at four
jobs then diverged (NDCG 0.00106 against the Go test's 0.36). Raw values: `rust-rejected-epoch-shards.txt`.
Merging every 256 updates keeps each shard close to the sequential order.

Gate (test `ml_100k_bpr_parallel_runs_match_go`): 12 Rust runs at four jobs, each compared with the
single-job Go run of the same configuration, measured in the same test on every run. Each Rust run must lie
within 0.01 of that reference for NDCG, precision and recall. The 12 Go runs at four jobs are printed as
evidence of Go's own spread and are not asserted.

Result on the head (release, `cargo test --release -p gorse-conformance --test metrics -- --nocapture
--test-threads 1`, log in `porting/notes/wp-3-8-parallel-runs/release-test-output-head.log`): 15 passed, 0
failed, 0 ignored, finished in 1927.35 s.

- Recall: 0.7709438 in all 12 Rust runs, against 0.7677625 (difference 3.2e-3, band 0.01).
- NDCG: 0.4991927 to 0.4991929, against 0.5013959 (difference 2.2e-3, band 0.01).
- Precision: 0.0770945, against 0.0767757 (difference 3.2e-4, band 0.01).

The 12 Rust runs are identical for recall. NDCG and precision differ only in the eighth significant digit.
The cause of those last digits is not verified; the parallel reduction in the evaluation is the likely one.

Cost: the full metrics suite took 1927 s on this container, against about 530 s before the fix. Most of the
extra time is the rounds at four jobs. Rounds of 256 are the chosen length; no other length was measured
on the head.
