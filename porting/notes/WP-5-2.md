## Deviations and notes

- **D-WP52-1: the SDK harness moved into a shared module.** The harness of WP-4-7 moved from `conformance/tests/mixed_cluster.rs` to `conformance/tests/common/sdk_suite.rs`, with no change in behaviour. `run_leg` split into `start_leg` (the nodes, the restore and the training wait) and the suite run, and `Mix::label` became public for the Leg B runner. `mixed_cluster.rs` keeps its four tests, the O-89 timing run and the stamp parser. Integration test files cannot import each other, so a shared module is the only way to reuse the harness.
- **D-WP52-2: the `gorse_rs` suite's entry point is the server's HTTP port.** The suite calls `http://127.0.0.1:8088/` with API key `zhenghaoz`. Port 8088 is the port at which `gorse-in-one` serves the REST API, as the printout of `cmd/gorse-in-one` shows. In a cluster the SDK's routes (`/api/user`, `/api/items`, `/api/feedback`, `/api/recommend/`, `/api/item/.../neighbors`) belong to the server (`server/rest.go`), and the master's `/api/` routes are its own (`master/rest.go`). So the port becomes `cluster.ports.server_http`. It is the same choice as `GORSE_SERVER_ENDPOINT` in the Go SDK harness. The API key and every assertion are unchanged.
- **D-WP52-3: the `gorse_rs` tests run in the order `cargo test` starts them.** The repo's tests are `#[serial]`, so their order is the order libtest starts them: by name, with `blocking::` first. The leg runs them in that order, one after another, and runs every test even after one fails. The suite is order-dependent (the expected neighbours and recommendations come from the restored dump and the earlier tests' writes), so the order is part of the port.
- **D-WP52-4: `gorse_rs` is vendored at `2de2691`, not taken from crates.io.** The crates.io 0.5.0 package has no tests. The suite and the client it calls must come from the same commit, so the repository's `src/lib.rs` is copied unchanged to `third_party/gorse-rs` (see its `GORSE.md`), and conformance uses it as a path dev-dependency. This follows `third_party/mongodb-3.9.1`.
- **X-WP52-1: the SDK legs use SQLite stores, not the 12 backends.** `Cluster::new_from_config` writes `sqlite://` store URIs, as `client/setup-test.sh` does. No backend is on the path of these legs. The thread has no Docker daemon, so `docker ps` prints nothing here. The court runs the backend gates on the merged head.
- **Environment flake, not a port result.** The first Leg A run failed before any leg started: `go build` of `server/rest.go` could not fetch `github.com/swaggest/swgui@v1.8.5` (`stream error: INTERNAL_ERROR`). `GoBuild::shared` caches the error for the whole test process, so all three legs failed together. `go mod download` succeeded on the first retry, and the rerun passed. No test was changed for this.
- The Go client's `go test` runs with `-count=1`, so no result is cached.
