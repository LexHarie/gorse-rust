# WP-2-8 notes: vector store core (storage/vectors/database.go, no_database.go, xvec.go)

Provisional ids; the integrator renumbers them into `PORTING.md` and
`PORTING_NOTES.md`. The Rust target is `crates/gorse-storage/src/vectors/`:
`mod.rs` (API types, the `Database` trait, `NoDatabase`, `open`), `xvec.rs`
(the `xvec://` store) and `suite.rs` (the shared suite, test-only).

## Plan corrections

- **C-WP28-1 The shared suite is run by the xvec tests only.** `testQuantization`
  in `database_test.go` is called only from the Qdrant and Milvus suites. It is
  ported in `suite.rs` and run for xvec with `QuantizationNone`, the one
  quantization xvec accepts (`xvec::tests::quantization_none`). WP-2-9 calls
  it with the other quantization types.
- **C-WP28-2 `Database` is an async trait with the caller's context.** Every
  Go method takes `context.Context`; the Rust trait takes
  `&gorse_common::gocontext::Context` first and is `#[async_trait]`, as the
  integrator ruled (D-122). This replaces the synchronous trait of the first
  head. The xvec store does its file IO and scans on tokio's blocking pool
  (`spawn_blocking`), and holds no std lock across an `.await`. WP-2-9 and
  WP-2-12 use the same shape.

## Decisions

- **D-WP28-1 Trait object.** `Database: Send + Sync` with `&self` methods, so
  `open` returns `Box<dyn Database>`. Go's mutable `sync.Map` state sits behind
  one `RwLock` per store and one per collection. The store is an
  `Arc<Store>`: each async method clones the `Arc` and its owned inputs, and
  runs the sync `Store` method on the blocking pool (`blocking` in `xvec.rs`,
  which resumes a task's panic on the caller). Nothing borrowed crosses an
  `.await`.
- **D-WP28-2 Errors.** `vectors::Error` is `Storage { kind, message }` (the
  storage sentinel plus Go's exact text, `kind()` is Go's `errors.Is`),
  `Context(ContextError)`, and `Other(String)` for everything else. The
  messages copy Go's `fmt.Errorf` texts, including the `collection X: not
  found` and `collection X already exists` forms.
- **D-WP28-3 Registry.** Go fills `creators` from `init` functions. Rust lists
  the backends in `vectors::open`, which is the same lookup by prefix. WP-2-9
  adds its prefixes there.
- **D-WP28-4 Enums.** `Distance` is an enum. `QuantizationType` is an enum with
  an `Other(String)` case, because Go's type is a string and `master/tasks.go`
  converts unchecked config strings into it.
- **D-WP28-5 Integers.** Go's `int` fields and arguments (dimensions, bits,
  `topK`, counts) are `i64`, as in `gorse-storage-core`, so the Go range checks
  stay.
- **D-WP28-6 Time.** `Vector.Timestamp` is `gotime::Time`. Storage keeps Go's
  `UnixMilli`.
- **D-WP28-7 Own file format.** D-6 decided that `xvec://` is Rust's own
  format. Each collection is a directory `<prefix><name>` holding one
  `gorse.vectors` log: a header (magic `GVECTORS`, version 1, dimension, distance
  code) and one record per upsert or delete. Writes are appended and synced
  before they are applied. A torn last record is dropped on open. `Optimize`
  rewrites the log. The layout is in the module header of `xvec.rs`.
- **D-WP28-8 Exact search.** The store scans every live vector and keeps the
  best `topK`. HNSW, which Go uses, is not ported (X-WP28-2).

## Deviations

- **X-WP28-1 Float16 bytes are copied.** Go's `Float16Bytes` and
  `Float16Values` reinterpret memory, so the two slices share storage and the
  conversions allocate nothing. The Rust functions copy and encode little-endian
  explicitly. `TestHalfBytes` keeps its value assertions (the hex string and the
  round trip). It drops the aliasing assertions (`values[0] = ...` changes
  `encoded`, `decoded[1] = ...` changes `values`) and the `AllocsPerRun` checks,
  which test Go's memory sharing, not the store's behaviour. Gorse only writes
  these bytes once, so nothing depends on the sharing.
- **X-WP28-2 Exact search, not HNSW.** Go's `xvec` answers queries with an
  approximate index. This port answers them exactly, so the Rust results are
  the true top `topK`. The results equal Go's where HNSW's recall is 1, and they
  differ by its missed neighbours otherwise. The ranking tolerance belongs to
  Phase 3 (metric parity); the open question is O-WP28-1. Cost: a query is O(n·d) over the collection, not
  sublinear. `NumJobs` and `SkipUnindexedSegments` are accepted and ignored,
  since exact search has no job count and no index to skip.
  Scores are xvec's, read from `internal/core/algorithm/distance_batch.go` and
  `internal/ailego/math/distance.go` at its pinned version:
  cosine `-(1 - cos)`, Euclidean `-(squared L2)`, dot the inner product. Ties
  go to the smaller id, which xvec leaves unspecified. A sparse query's dot
  product sums the query's overlapping indices in the vector's index order,
  which can round differently from xvec's merge.
- **X-WP28-3 The xvec format is Rust's own (refines X-1).** X-1 says a master
  switched between Go and Rust on one `xvec://` directory rebuilds its
  collections on its first training round. This port makes that true like so:
  `Init` skips a collection directory whose `gorse.vectors` is missing or lacks
  the magic, and logs a warning. Go's xvec directories therefore do not load.
  `AddCollection` on a name whose directory holds no log of this format removes
  that directory and creates the collection. The removal is preceded by a
  warning that names the directory. Such a directory is derived data
  the master rebuilds, but the removal is not reversible. A directory with a log
  of this format and no open collection is an error.
- **X-WP28-4 Collection names are checked.** The empty name, `.`, `..`, and
  names containing `/` or `\` are rejected with `invalid collection name`. Go
  joins the name into the path, so `a/b` creates a nested directory that
  `Init` never reads again (it lists one level), and `..` escapes the store
  root. Gorse builds names from the config's item-to-item and user-to-user
  names, so this follows X-2 in spirit: names are checked, not trusted.
- **X-WP28-5 The collection schema is fixed at creation.** `DescribeCollection`
  reports `QuantizationNone` and `Bits` 0 always, as Go does. The store does
  not keep `Bits`, and it rejects any quantization other than none with Go's
  text `quantization type sq for xvec not supported`.

## Go quirks reproduced

- **Q-WP28-1 Empty requests skip the collection check.** `AddVectors` with no
  vectors and `GetVectors` with no ids return success for a collection that
  does not exist. `QueryVectors` with `topK <= 0` returns an empty result
  before the check too.
- **Q-WP28-2 Query and get timestamps differ.** `GetVectors` returns
  `time.UnixMilli(ms).UTC()`, and `QueryVectors` returns `time.UnixMilli(ms)`
  in the local zone. Both are reproduced.
- **Q-WP28-3 `DeleteCollection` restores on failure.** If xvec's `Destroy`
  fails, Go stores the collection back in the map. The port does the same.
- **Q-WP28-4 `Close` is idempotent**, and every call after it fails with
  `xvec database is closed`, except a second `Close`, which succeeds.
- **Q-WP28-5 `DeleteVectors` removes timestamps strictly before the cutoff.**
  A vector written exactly at the cutoff stays.
- **Q-WP28-6 `GetVectors` returns vectors in the order of the ids**, each id
  once, and skips missing ids (`orderVectors`).
- **Q-WP28-7 `NoDatabase.Optimize` succeeds.** Every other `NoDatabase` method
  returns `storage.ErrNoDatabase`.

## Open

- **O-WP28-1 HNSW ranking parity.** Go's `xvec` answers with HNSW, which is
  approximate. This port scans exactly (X-WP28-2), so its top `topK` can differ
  from Go's where HNSW misses a neighbour. Option: `gorse_common::ann::Hnsw`
  (WP-1-10) as the index. That would bring the rankings closer to Go's, but not
  identical, since the graph build differs. The exact scan costs O(n·d) per
  query. Phase 3 (metric parity) decides whether that gap is acceptable, and
  whether xvec's index must be ported.
- **tokio version.** The crate uses tokio 1.53.3, the version in `Cargo.lock`.
  `cargo info tokio` (checked 2026-10-28) reports 1.54.1 as the latest. Moving
  to 1.54.1 changes the lock for every crate that uses tokio, so this head does
  not do it. The integrator decides.
