# WP-2-2: SQL data store (MySQL, PostgreSQL, SQLite)

Ports `storage/data/sql.go` and `storage/data/sql_test.go` @ add21b5 into
`crates/gorse-storage/src/data/sql/` (root `sql.rs`; submodules `open`,
`query`, `time`, `schema`, `search`, `items`, `users`, `feedback`, `sqlite`,
`tests`). Provisional ids: the integrator folds them into PORTING.md and
PORTING_NOTES.md and deletes this file.

## Decisions (D-WP22-n)

- **D-WP22-1: one build, all three dialects.** The store is compiled only when
  `mysql`, `postgres` and `sqlite` are all on (`cfg(all(...))` in `data/mod.rs`
  and in `data::register_builtin`). Go links all three drivers into every binary.
  The alternative was a `cfg` on every `Pools` variant and every dispatch arm.
- **D-WP22-2: explicit SQL on sqlx 0.9.** One generic query layer
  (`sql/query.rs`) binds every value (`Bind`). The dialect differences are
  written out per module. Text passed to `sqlx::query` is wrapped in
  `AssertSqlSafe` (sqlx 0.9 requires the assertion for any dynamic text). Each
  wrap is justified at the site: the text holds only literals, the table names
  from the operator's prefix, and placeholders. The `SET` statements come from
  the operator's DSN.
- **D-WP22-3: `json_contains` through the SQLite C API.** sqlx-sqlite 0.9 has no
  scalar function API, so `sql/sqlite.rs` calls `sqlite3_create_function_v2`
  on each connection's handle in `after_connect`. The `unsafe` is confined to
  that module (`#![allow(unsafe_code)]` with a reason; a `SAFETY:` comment on
  every block). Argument and error rules come from
  `gorse_storage_core::json_contains`.
- **D-WP22-4: streams run on a task.** Each stream runs its query on a spawned
  task and sends batches over `mpsc(1)`, as Go's `GetItemStream` sends over a
  goroutine with `bufSize = 1`. The context is checked before each batch. The
  item stream keeps items at or after `time_limit` (`>=`), as Go does.
- **D-WP22-5: `AssertSqlSafe` and the audit.** See D-WP22-2. No request data is
  ever written into SQL text. Every user value is bound.

## Deviations (X-WP22-n)

- **X-WP22-1: `Init` creates, it does not migrate.** Go's `Init` runs GORM
  `AutoMigrate`, which also alters tables that already exist. The port runs
  `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS`. A fresh database
  dumps byte-identical to Go's (see Evidence). A database created by an older Go
  version is not altered. A second Go `Init` on the same database runs
  introspection and `ALTER TABLE ... SET DEFAULT` on the existing columns, with
  the defaults they already have, so the schema does not change. The port runs
  none of these statements.
- **X-WP22-2: `ErrNotFound` is the bare sentinel.** Go wraps it with the id
  (`item X not found`). The port returns `Error::Storage(NotFound)`, so the kind
  matches and the message does not.
- **X-WP22-3: pool size defaults differ.** Go's `MaxOpenConns` unset means no
  limit. sqlx's default is 10 when the option is not set.
- **X-WP22-4: `MaxIdleConns` is not applied.** sqlx has no cap on idle
  connections, so the option is ignored. `ConnMaxLifetime` and `MaxOpenConns`
  are applied.
- **X-WP22-5: MySQL DSN parameters.** The store adds `sql_mode`, the isolation
  variable and `parseTime` as Go does. Every other DSN parameter that is not a
  driver option is run as `SET name = value` on connect, as go-sql-driver does.
  The driver's own options (`tls`, `charset`, `collation`, `loc`, timeouts,
  `interpolateParams`) are not mapped. sqlx's defaults apply to them.
- **X-WP22-6: SQLite URL parameters.** The file is the part before `?`. The two
  pragmas Go adds (`busy_timeout(10000)`, `journal_mode(wal)`) are applied. Other
  `_pragma` values in the URL are ignored.
- **X-WP22-7: PostgreSQL TLS default.** lib/pq requires TLS when `sslmode` is
  unset. sqlx defaults to `prefer`. This is not checked against a TLS server, so
  deployments that depend on the default should set `sslmode=require` explicitly.
- **X-WP22-8: the MySQL timezone case reports a pass.** Go's
  `testTimezone` calls `Skipf` for MySQL. The shared suite here returns without
  assertions for `TimeStamps::Unknown`, so `cargo test` shows the MySQL case as
  a pass where Go shows a skip. No assertion is lost; the reporting differs.

## Quirks (Q-WP22-n)

- **Q-WP22-1: PostgreSQL `Reconcile` rebuilds an unchanged search index.
  Resolved, and Go does the same.** The server rewrites the index definition
  (`'simple'::regconfig`, `COALESCE((categories)::text, ''::text)`), so Go's
  containment check never matches. Go's `Reconcile`, run twice on the same
  database, drops and recreates `gorse_search_index` both times, as the port
  does. With `log_statement = 'all'` on PostgreSQL 10.0, the second `Reconcile`
  on each side runs the same statements: `SELECT indexdef FROM pg_indexes ...`,
  `DROP INDEX IF EXISTS gorse_search_index`, then `CREATE INDEX
  gorse_search_index ON xo_items USING GIN (...)`. MySQL's check is ported the
  same way and is not observed.
- **Q-WP22-2: SQLite `Reconcile` rebuild. Resolved, and matches Go.** A
  sentinel row inserted into `gorse_search_index` survives a `Reconcile` with
  unchanged columns, so the index and triggers are not rebuilt. After a
  `Reconcile` with changed columns the sentinel is gone, so they are rebuilt.
  Go and the port give the same result in both cases.
- **Q-WP22-3: labels NULL versus "null".** Go writes a nil feedback label as SQL
  `NULL`. Items and users store the JSON text `null`. The port matches, and the
  missing-id rows the feedback write inserts use `'null'` for users and items.
- **Q-WP22-4: time text per driver.** MySQL truncates `time_stamp` to whole
  seconds. `update_at` is `datetime(6)` and keeps microseconds. PostgreSQL
  rounds to microseconds. SQLite stores modernc's `time.String()` form (UTC, with
  `+0000 UTC`) and reads it back with a hand parser that follows modernc. The
  suite's timezone case covers PostgreSQL and SQLite.
- **Q-WP22-5: SQLite time comparison is textual.** Go's `time_stamp <= DATETIME()`
  compares text, so rows in the same second with a fraction compare greater. The
  port keeps the same comparison.
- **Q-WP22-6: counts are estimates on MySQL and PostgreSQL.** Go's `Count*` reads
  `SHOW TABLE STATUS` (MySQL) and `reltuples` (PostgreSQL). The port does the same.
  The suite runs `ANALYZE` before counting on PostgreSQL, as Go's `analyzeTables`
  does. Before `ANALYZE`, a freshly written PostgreSQL table counts 0, in Go and
  in the port alike.
- **Q-WP22-7: one statement per batch.** Each write batch is one `INSERT`, as
  the Go code in this file writes it. Batches larger than the server's
  placeholder limit are not tested.

## Open items (O-WP22-n)

- **O-WP22-1: the Go-to-Rust read path. Run, and it matches.** Go populates a
  database and Rust reads it, and the reverse, on PostgreSQL 10.0, MySQL 8.0 and
  SQLite (see Evidence). Each run calls `Reconcile` with the five columns before
  it reads, as the application does at start-up. Search needs the vector that
  `Reconcile` sets, in both implementations.
- **O-WP22-2: O-36.** The brief asks for the shared suite against each backend,
  which closes O-36 with the MongoDB data store. The SQL half passes. The
  integrator closes the item.
- **O-WP22-3: Q-WP22-1 and Q-WP22-2 need Go runs.** Done, see above. Nothing
  is open here.

## Evidence

Services: MySQL 8.0.46 (`mysql:8.0`), PostgreSQL 10.0 (`postgres:10.0`, the
version `.github/workflows/build_test.yml` pins, so CI tests 10.0 and so does
this port; newer versions are not tested), MariaDB 10.2.44 (`mariadb:10.2`, CI's
MariaDB job), SQLite bundled through libsqlite3-sys 0.37.0. All three suites run
`database_test::run`. No skips on the three-service run (`grep -c skipping` on
the log is 0). On MariaDB, Go's `TestMySQL/TestTimezone` skips as it does on
MySQL (X-WP22-8).

```
MYSQL_URI=mysql://root:password@tcp(127.0.0.1:3306)/ \
POSTGRES_URI=postgres://gorse:gorse_pass@127.0.0.1:5432/ \
cargo test -p gorse-storage --features mysql,postgres,sqlite data::sql
test data::sql::tests::test_sqlite ... ok
test data::sql::tests::test_postgres ... ok
test data::sql::tests::test_mysql ... ok
test result: ok. 3 passed; 0 failed; 0 ignored
```

Schema dumps (Rust-created, `contracts/tools/dump-schemas.sh` format, compared
with `contracts/schema/data/`): `mysql.sql`, `mysql.search.sql`, `sqlite.sql`,
`sqlite.search.sql`, `postgres.sql` and `postgres.search.sql` are byte-identical
to the committed Go-generated files. The PostgreSQL files needed one trailing
newline from the dumper, which is in the dump script, not in the store.

Cross-compatibility, one fixed fixture (4 users, 6 items, 6 feedback rows, one
with a NULL label and one with a nil item categories list). Each side calls
`Reconcile` with the five columns, then reads every user, item and feedback
row, the search ids for three queries and the three counts, as canonical
sorted JSON lines (25 lines). Every database is `ANALYZE`d before the reads.

- PostgreSQL 10.0, MySQL 8.0 and SQLite: Go populates and Rust reads; Rust
  populates and Go reads; and the two populated outputs match each other. All
  nine comparisons are byte-identical.
- MariaDB 10.2.44: Go `TestMySQL` and Rust `test_mysql` pass. Cross-compatibility
  is not run on MariaDB.

Go's `Reconcile` on PostgreSQL, run twice, with statement logging (see Q-WP22-1)
and the SQLite sentinel probe (see Q-WP22-2) were run against the Go oracle.
