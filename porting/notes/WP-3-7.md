# WP-3-7 notes (recommend), provisional ids

The integrator folds these into PORTING.md and PORTING_NOTES.md. Ids in code
comments are existing ones (O-75, O-76, O-30); the new items below have no id
in code, so the fold can renumber them freely.

Port: `logics/recommend.go` @ add21b5 to `crates/gorse-logics/src/recommend.rs`,
with its suite in `recommend/tests.rs`. Go-interop oracle:
`contracts/tools/recommendgolden` and `conformance/tests/recommend_oracle.rs`.

## Decisions

- **D-WP37-1 `Source` replaces Go's closures, and `run` takes `&mut self`.** Go's
  `parse` returns a `RecommenderFunc` closure. The port returns a `Source` enum
  and runs it in `Recommender::run`. `recommendItemToItem` sorts the user's
  feedback in place (`data.SortFeedbacks`), and the port does the same, so the
  item-to-item run takes `&mut self` and leaves the sorted feedback behind, as
  Go does.
- **D-WP37-2 The external script runs on a blocking thread.** `External::new` and
  `pull` use `reqwest::blocking` and `rquickjs`. Run on the async worker they
  would block it or panic. The port builds and runs the script inside
  `tokio::task::spawn_blocking`. Go's goroutine has no such limit.
- **D-WP37-3 `Recommend` returns a `Vec`, and nil is not kept.** See O-76 below.

## Quirks and deviations

- **Q-WP37-1 Go walks a map before the top-k.** `recommendItemToItem` and
  `recommendUserToUser` push their candidates from a `map`, so ties in the heap
  come out in Go's random map order. The port pushes in ID order (`BTreeMap`),
  so a tie is always broken the same way. Go has no fixed order to match.
- **X-WP37-1 A negative cache size maps to 0.** Go's `make([]T, 0, n)` panics on
  a negative `CacheSize`. The config validates `cache_size` with `gt=0`, so the
  config loader never passes one. Only a hand-built `RecommendConfig` can.
- **X-WP37-2 The not-found errors wrap `StorageError::NotFound`.** The texts
  are `item-to-item recommender NAME not found` and `user-to-user recommender
  NAME not found`, as Go's `%w` with `storage.ErrNotFound` gives them. The
  unknown-name text is `unknown recommender: NAME`, as Go's `errors.Errorf`.
- **X-WP37-3 Each Rust test opens its own stores.** Go's suite shares one set of
  stores between its methods. The expectations hold on fresh stores (no method
  reads a row another writes), so the Rust suite gives each test its own.
- **X-WP37-4 The ported suite does not cover the user-to-user digest for type
  `items`.** The Go test's user-to-user config is type `embedding`, and the
  digest reads the feedback types only for type `items`. A mutation that hashes
  with `None` survives the ported suite. The oracle covers every kind, including
  `items`, and its digests match Go.
- **X-WP37-5 `lo.Every` takes the collection first.** `lo.Every(collection,
  subset)` is true when every element of `subset` is in `collection`. Go's
  `lo.Every(item.Categories, r.categories)` therefore requires the item to carry
  every requested category. The first draft of the port reversed the two, and
  the unit suite did not catch it (its user-to-user case requests no category).
  The oracle did, with 34 differences, and the fix is in the code with a comment.
  Recorded here so the court sees the bug and its fix.
- **X-WP37-6 `Recommend` takes the limit as `i64`.** Go's `int`. A limit of 0 or
  less means all. A negative cache size is the same case as X-WP37-1.

## Open items

- **O-76 (extended): Go can return nil where the port returns an empty `Vec`.**
  Go's `RecommendSequential` and `Recommend` return a nil slice when nothing is
  appended to a nil `result`, so the list stays nil. The port cannot tell the
  two apart. The oracle records the nil-ness and counts it: 46 to 48 of the 120
  runs, in repeated runs, give a nil result in Go. The REST work (`server/rest.go` and `master/rest.go`)
  must check both encodings, as X-201 asked.
- **O-30 (extended): Go's dense neighbour search is approximate and varies
  between builds.** `xvec` stores dense vectors as FP16 in an HNSW index, and the
  graph is built with random levels. Two builds of the same rows can give
  different neighbour sets, so the Go recommender is not reproducible on dense
  collections. Sparse collections use Go's flat index, which is exact. The
  oracle keeps a case only when three independent builds of its stores give the
  same outcomes (`stableCase` in the generator). A case that never settles fails
  the generator. The Rust store is exact, so its results match the stable Go
  outcomes; a stable but approximate Go answer would show as a difference.
- **Oracle scope.** The external recommender is covered by the ported `TestExternal`
  only. The oracle does not start a script server, so it does not compare
  `external/` runs.
- **O-75 and Q-255 are not touched.** `recommend` takes the processed items from
  the stores, not from the master, so O-75 stays with the master work package.
  Recommend evaluates no expressions, so Q-255 does not apply here.

## Evidence

- Largest score difference between Go and Rust over the oracle: 4.77e-7 (one
  FP32 ulp at magnitude 4 to 8, from the FP16 dense vectors). The tolerance is
  1e-6 relative to max(|s|, 1).
- Mutation checks on the ported suite: M1 (latest keeps excluded items) and M2
  (user-to-user shows hidden items) fail the suite. M3 (user-to-user digest with
  `None`) survives it, as X-WP37-4 explains.
- Mutation check on the oracle: reversing the `lo.Every` arguments fails it with
  34 differences.
