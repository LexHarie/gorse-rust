# WP-3-6 notes (non-personalised, external, reranker logics; expr checker, compiler, VM)

Branch `claude/wp-3-6-logics-expr`. Provisional ids: D-WP36-n, Q-WP36-n, X-WP36-n, O-WP36-n.

## Spike: the `expr-lang` 2.1.0 crate (D-WP36-1)

Brief step 2 (crate-selection.md, row expr-lang/expr): evaluate `expr-lang` 2.1.0 against the
Go oracle corpus and keep it only if it passes. It does not. Scratch project outside the repo.
Corpus: `crates/gorse-expr/testdata/corpus/` (1330 cases, golden from expr-lang v1.17.8).

| Verdict over the 1327 non-volatile cases | Count |
|---|---|
| both reject, compile error | 391 |
| both reject, runtime error | 77 |
| values agree | 652 |
| values differ (int vs float from JSON, Go type names) | 166 |
| spike rejects where Go gives a value (`item.Timestamp.Unix()`, `now() - time`) | 27 |
| spike accepts where Go rejects at compile time (`1 == 'a'`, `nil?.a`, `$env[...]`) | 12 |
| spike returns nil where Go gives an index-out-of-range error | 6 |
| spike panics on valid Go syntax (`map {'b': 2}`) | 2 |

Reasons it is rejected: (1) no static type checking, which Gorse needs (`Node().Type().Kind()`
must be numeric for a score and bool for a filter, `non_personalized.go`); (2) error texts
differ from Go's `file.Error` format; (3) no Go `time.Time` and `time.Duration` semantics on
values built from Go structs; (4) panics on valid input; (5) no `;` sequences.
So the checker, compiler and VM are a hand port (D-10), in `gorse-expr`.

## Gate for the golden corpus

`contracts/tools/exprevalgolden` runs `expr.Compile` and `expr.Run` in the four environments
Gorse uses (`non_personalized`, `item`, `user`, `none`). `contracts/tools/exprcorpus/extract.py`
builds `expressions.json` from the Go tests, configs, the expr-lang docs (`expr` blocks) and
synthetic cases. Calls to `now()` that return a time or duration are volatile.

Found by the oracle: `Compile` runs the optimizer by default (`conf.CreateNew`, `Optimize: true`),
so `1 % 0` fails at compile time with "integer divide by zero". The port needs constant folding
with the same errors.

## Architecture of the hand port (D-WP36-2)

Module layout under `crates/gorse-expr/src/`, one Go package each:

- `ty.rs`: the reflect type model `Ty` (Go `reflect.Type`): `Bool`, the int and uint
  kinds, `Float32`, `Float64`, `String`, `Interface` (`interface {}`), `Slice`, `Map`,
  `Func`, `Struct` (named, with fields and embedded flags), and the named kinds
  `time.Time` (struct) and `time.Duration` (int64). `Display` is Go's `reflect.Type.String()`.
- `nature.rs`: the checker's `Nature` (Go `checker/nature`): `ty`, `nil`, `is_integer`,
  `is_float`, `strict`, `reference` (Go `Ref`), env `fields`, builtin `func` index.
- `value.rs`: the runtime `Value`, Go's `any`: one variant per Go kind (so `%T` and
  the interface-conversion messages are exact), `Time`, `Duration`, typed `Slice`,
  `Map` (ordered entries), `Struct` (type and field values).
- `checker/`, `compiler.rs`, `vm/`, `builtin/`, `optimizer/`: one file per Go file.
- `conf.rs`: the `Config` with `env`, `expect`, `optimize`, `strict`, `short_circuit`,
  `max_nodes`, `disabled`, and the function tables.

Deliberately not ported (not reachable from Gorse's API, `Compile(src, Env(map))`):
the patcher and `Visitor` options, `ConstExpr`, the Go `Function`/`Operator`/`Patch`
options, `Profile` spans, the `Debug` VM and `SafeFunction`/`OpCallSafe`. The typed
fast-path opcodes (`OpEqualInt`, `OpCallFast`, `OpCallTyped`, `OpCallBuiltin1`,
`OpFetchField`, `OpLoadFast`) are emitted only where Go's optimizer or the type
checker chooses them; the port uses the generic opcode, whose result and error text
are the same by construction (checked by the corpus, `PORTING_NOTES.md` X-WP36-n).

Struct values are built from the Gorse data types in Rust (`EnvTypes` builds the Go types
`data.Item`, `data.Feedback` and `data.FeedbackKey`; `NonPersonalized` builds the values),
so that the `Ty` matches the Go struct: field names, the embedded `FeedbackKey`,
`time.Time` and `any`.

## Non-personalised logic (`non_personalized.rs`)

Port of `logics/non_personalized.go` @ add21b5, with the six tests of
`non_personalized_test.go` as `non_personalized::tests`. The expressions compile with
`item` typed `data.Item` and `feedback` typed `[]data.Feedback`, through
`nature::map_env_of` (added to `gorse-expr`; `map_env` now delegates to it).
Go's `Compile` errors and the two type errors (`score function must return float64`,
`filter function must return bool`) are the same texts. `Push` and `PopAll` keep Go's
order: hidden items and filter misses are skipped, the score's type switch is Go's, and
the groups are `""` (all items) and each category.

## Deviations (D-WP36-n)

- D-WP36-3: `NonPersonalized` is not `Send`, and `push` and `pop_all` take `&mut self`
  with no mutex. Compiled programs hold `Rc`s (`Ty`, `Value`). Go's `Push` is called from
  `parallel.Parallel` workers (`master/tasks.go`, lines 607-630) and is safe to call
  concurrently. See Q-WP36-1.
- D-WP36-4: a `json.Number` in `Labels` becomes `Value::Float`. expr-lang has no type for
  `json.Number`, and `Value::Integer` covers only `int64`, `time.Month` and `time.Weekday`.
  So `len(item.Labels)` and string comparison on a numeric label differ from Go. See Q-WP36-2.
- D-WP36-5: the integer kinds of expression values are `int` (`Value::Int`), `int64`
  (`Value::Integer`), `time.Month` and `time.Weekday`. The score accepts a float, an `int`
  or an `int64`, which is all Gorse's expressions produce; Go's other integer kinds are
  not in the port.
- D-WP36-6: pointers are not modelled except `*time.Location`, and only map environments
  are ported (`expr.Env` of a struct is not). Gorse uses only map environments.
- D-WP36-7: the methods of `time.Time` that return several values (`Date`, `Clock`, `Zone`,
  `ISOWeek`) are not exposed. An expression that calls one fails to compile here; Go compiles it.
- D-WP36-8: set constants (`x in [...]` folded by the optimizer) are typed
  `map[int]interface {}`, not `map[int]struct {}`. Only `%T` output differs.
- D-WP36-9: `pow` uses `f64::powf`, not Go's `math.Pow`, so the last bit can differ for some
  inputs. The corpus agrees on all its `pow` cases.
- D-WP36-10: the duplicate-name rule of `encoding/json` (dominance of embedded fields) is not
  ported in `toJSON`. Gorse's structs have no such duplicates.

## Open questions (Q-WP36-n)

- Q-WP36-1 (for the integrator): how the master pushes into non-personalised recommenders.
  Go pushes from several goroutines; the port's recommender is single-threaded. Either the
  master pushes on the thread that owns the recommender, or the expression types move to
  `Arc`. The master port (a later WP) must choose.
- Q-WP36-2: should the port keep a `json.Number` as its own named string type, as Go does?
  That needs a named-string value in `gorse-expr`. It matters only for expressions that
  read a numeric label.
- Q-WP36-3: each `push` converts the item and every one of its feedback into expression
  values, which costs O(feedback) per item. Measure it in the WP-3-8 replay before optimising.

## Oracle notes (O-WP36-n, X-WP36-n)

- X-WP36-1: the `expr-lang` module in the Go module cache is a Gorse-patched v1.17.8
  (`optimizer/sum_range.go` has a `reduce(m..n, #+#acc)` closed form, and
  `optimizer/count_threshold.go` sets `Builtin.Threshold`). The port follows the patched code.
- O-WP36-1: the corpus compares results that depend on map order as multisets (a list
  result is compared up to order), and it does not compare booleans that depend on map order.
  Go's map order is random, so the oracle has no fixed answer there. This narrows the
  oracle's coverage of `keys`, `values` and `toPairs` (`crates/gorse-expr/tests/corpus.rs`).
- O-WP36-2: `const_expr` (`ConstFns`) is not run. Gorse configures no `ConstFns`, and Go
  skips that pass when there are none.
