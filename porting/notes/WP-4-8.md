# WP-4-8: `gorse-bench`

Port of `cmd/gorse-bench/main.go` (600 lines, one file, no Go tests) at `add21b5`
as the `gorse-bench` binary of `gorse-cmd`. The Go oracle is built with `go build`
and run in the golden test.

## Where it lives

| Rust | Ports |
|---|---|
| `crates/gorse-cmd/src/bench.rs` | the cobra command tree, its flags, its help layout, the dispatch, and the dataset load both evaluating subcommands share (`runRankingBenchmark` and `benchEmbeddingCmd` call `config.LoadConfig`, `master.NewMaster`, `data.Open` and `LoadDataFromDatabase` in that order) |
| `crates/gorse-cmd/src/bench_ranking.rs` | `reranker` and `decision`: `runRankingBenchmark`, `EvaluateAFM`, `EvaluateReranker`, `EvaluateDecision`, `evaluateRanker` |
| `crates/gorse-cmd/src/bench_embedding.rs` | `embedding`: `benchEmbeddingCmd`, `EvaluateEmbedding`, and the OpenAI embeddings call |
| `crates/gorse-cmd/src/bench_table.rs` | tablewriter v1.1.4's default renderer, for the tables the tool prints |
| `crates/gorse-cmd/src/bin/gorse-bench.rs` | the binary |
| `contracts/cli/gorse-bench.help.txt`, `gorse-bench-{reranker,decision,embedding}.help.txt` | the Go `--help` output, generated from the pinned build |
| `conformance/tests/bench_golden.rs` | the golden comparison (WP-4-8 step 4) |

The help files are the pinned binary's output. The root and the three subcommands
are checked byte for byte against them (`bench/tests.rs`). The `-j` default is
`runtime.NumCPU()` on the machine that built the Go binary, so the root check
substitutes this machine's CPU count for `(default 4)`. The Rust side reads the
same value, so the check holds on any machine.

## Deviations

- **D-WP48-1 `completion`.** cobra generates the shell scripts. This port does not:
  `gorse-bench completion` prints its own help, and `completion bash` is an unknown
  command (exit 1). The help of `completion` therefore differs from Go's, and no
  contract file covers it. The root help, which lists `completion`, matches.
- **D-WP48-2 help layout.** clap does not write the help. `help_text` lays it out
  from the command's metadata, as cobra and pflag do (sorted commands, sorted flags,
  the help column three past the longest flag, pflag's default rules).
- **D-WP48-3 logs.** Go's zap writes to stderr. `common/log::set_logger` sends the
  main log to stdout, which would corrupt the tables, so the tool installs a stderr
  subscriber of its own. Log texts and levels are not compared.
- **D-WP48-4 progress bars.** Go's `progressbar` writes to stderr and is not ported.
- **D-WP48-5 row order.** Go's `sync.Map` lists the GAUC and embedding rows in a random
  order. Rust sorts them by name. The golden test sorts the Go rows too.
- **D-WP48-6 AFM seed.** Go seeds its global random source at random, and the AFM
  weights draw from it. Under `GODEBUG=randautoseed=0` Go seeds it with 1, and the
  Rust bench reads the same variable and seeds its AFM with 1 (`Afm::set_init_seed`).
  Without it, two Go runs already differ. The golden test sets the variable for both
  tools.
- **D-WP48-7 processed labels.** Go's `cfDataset.GetItems()` returns items whose labels
  are *processed* (`dataset.AddItem` runs `processLabels`). The Rust `DatasetItem`
  holds the same processed form, so the embedding expressions see what Go's do. The
  reranker and decision APIs get `data.Item` values, which must be storage labels, so
  `to_item` writes the processed numbers (ids and FP16 bits) as `Labels::Number`. A
  template that prints a labelled item may therefore render differently from Go. The
  golden test's templates are constants, so the golden does not exercise this.
- **D-WP48-8 OpenAI request types.** WP-4-3 and WP-4-4 export no OpenAI client, so
  `bench_embedding.rs` holds a minimal one: `POST {base_url}/embeddings`, bearer
  token, a body of `input`, `model`, and `dimensions` only when non-zero (go-openai's
  `omitempty`), and the first embedding of the response (`resp.Data[0]`). A response
  with no embedding is an error here, where Go panics.
- **D-WP48-9 failures.** Fatal messages keep Go's text and exit 1 (`cli::fatal`). A
  usage error exits 1, as cobra's does (`cli::parse`).
- **D-WP48-10 dimensions.** An embedding of a different length from the first one is
  fatal, as Go's `Fatal` is ("inconsistent embedding dimensions").

## Cross-crate changes (flagged)

- **X-WP48-1 `gorse-master`.** `Master::load_benchmark_dataset(&self, parent,
  database, cfg)` in `tasks/load.rs`, the thin `pub` wrapper the coordinator approved.
  It builds the online evaluator itself (`metrics::new_online_evaluator` with the two
  feedback type lists, as Go's `NewOnlineEvaluator(PositiveFeedbackTypes,
  ReadFeedbackTypes)`), because the metrics module is private and the bench cannot
  build the evaluator to pass in. That is why the signature has no evaluator argument.
  No other `gorse-master` file changed.
- **X-WP48-2 `gorse-logics`.** `item_type`, `item_value` and `compile_column` in
  `item_to_item.rs` are `pub` (visibility only, no logic change). The embedding
  benchmark uses them to build the `item` environment. The earlier plan copied about
  130 lines instead, and I changed that to avoid two copies of the same typing rules.
- **X-WP48-3 `gorse-cmd`.** New `[[bin]] gorse-bench`, and dependencies on
  `gorse-dataset`, `gorse-expr`, `gorse-logics`, `gorse-model`, `gorse-model-core`,
  `gorse-storage`, `gorse-storage-core`, `serde`, `tracing-subscriber`, and reqwest's
  `json` feature. `Cargo.lock` gains the matching entries.

## Quirks and limits

- **Q-WP48-1 summation order.** Go visits users in map order, and its per-user sums
  are float32. Rust visits them sorted, so the last digit of a score can differ. The
  printed metrics have four decimals, so the difference is far below the printed
  unit.
- **Q-WP48-2 the reranker mock.** `gorse_common::reranker::MockServer` scores each
  candidate by its position, so the candidates the bench sends (negatives first,
  then positives) give the positives the lowest scores. Both tools report GAUC
  0.0000 for that ranker. The row checks the plumbing and the table, not a model.
- **Q-WP48-3 `--embedding-column`.** The `[]float32` result check is typed, but no
  run in this WP exercised it. The golden and the cross-check use `--text-column`.
  The float32 path is untested here and is the first thing to run on MySQL.

### Local cross-check on SQLite (not committed)

The golden test's comparison, run on a SQLite store with the Go oracle's
`gorse-bench` and the Rust `gorse-bench` on one config. The scratch copy of the test
was removed after the run. Both tools got the same mocks (`gorse_common::mock`'s
OpenAI and reranker mocks, and a decision mock that answers by question id), and the
run used `GODEBUG=randautoseed=0`.

- Dataset tables: identical (480 total, 390 train, 90 test; 190/200 and 50/40
  positive/negative).
- `reranker`: AFM 0.5833 and `golden-reranker` 0.0000, identical in both. CSV rows
  identical within 1e-4.
- `decision`: AFM 0.5833 and `golden-decision` 0.5208, identical in both. CSV rows
  identical within 1e-4.
- `embedding --text-column item.Comment -k 5 -s 3`: `golden-embedding (16)` with NDCG
  0.0210, precision 0.0067, recall 0.0333, identical in both.

The embedding case ran as follows. Both tools posted to `openai.base_url` on
`127.0.0.1`, which the sandbox's `NO_PROXY` covers, so the proxy was not used. The
mock answered `/v1/embeddings` with the MD-5 embeddings of `gorse_common::mock`,
which is the Rust port of the Go mock in `common/mock/openai.go`. The Rust client
reached it through reqwest's blocking client.

The first cross-check runs found two problems in my own work, and both are fixed:

1. The synthetic data put every positive before every negative, so the user-time
   split left only negatives in the test set and every AUC was 0. The golden now
   shuffles each user's kinds over the timeline.
2. The Rust tool wrote its logs to stdout, because `common/log::set_logger` always
   sends the main log there. It now uses a stderr subscriber.

## In-one playground import (court brief)

- `crates/gorse-cmd/src/in_one.rs`: the fetch, gunzip and restore moved into
  `restore_playground(master, base_url, name) -> Result<(), ImportError>`.
  `import_playground` passes the unchanged `PLAYGROUND_URL` and keeps its messages
  and exit codes. No env var, flag or config was added.
- `crates/gorse-cmd/tests/playground.rs`: the new
  `playground_github_restores_the_dump_and_serves` is not ignored. It reads
  `/mnt/project-files/datasets/github.bin.gz`, serves it from a loopback axum
  server, and imports it through `restore_playground` with that base URL. It then
  checks the counts, binds the in-one HTTP listener (`master::bind_http`,
  `master::serve_http`) and expects `GET /api/users?n=1` to return 200. The
  ml-100k test stays ignored with its O-1 reason.
- The test takes about 110 s in a debug build. Its loopback request goes through
  reqwest, which needs `127.0.0.1` in `NO_PROXY` where an HTTP proxy is set (it is
  in this sandbox).

Counts (the dump's sha256 starts `29be90c7`):

| Count | In the dump | Stored after the import |
|---|---|---|
| users | 2,079 | 2,079 |
| items | 22,320 | 22,320 |
| feedback | 357,294 | 331,901 |

**Feedback is 25,393 rows short of the brief's figure.** The brief's 357,294 is the
dump's record count, and the store holds fewer rows. 25,393 dump records name a
user that the dump's user stream does not hold. The restore writes feedback with
`insertUser` false, and Go's SQL `BatchInsertFeedback` drops those rows
(`storage/data/sql.go:1192`). The Rust port does the same (`retain_known_ids` in
`crates/gorse-storage/src/data/sql/feedback.rs`). The 331,901 stored rows are exactly
the records whose user and item are both in the dump. A separate framing reader
over the decompressed dump counted 357,294 records, all distinct by (type, user,
item), 25,393 with an absent user and none with an absent item. The Go binary was
not run for this count; the match rests on the Go source and the arithmetic. The
test asserts both numbers: 357,294 records in the dump, and 331,901 stored.

## Go interop: the GitHub restore (court brief)

`conformance/tests/playground_restore.rs` restores the same GitHub dump through two
masters and counts the rows each run stores, reading the SQLite files directly:

- The Go master, built by `GoBuild::shared()` at the pinned `add21b5` tree, starts
  on a fresh SQLite data store (`Cluster::new_with_store`). The decompressed dump is
  sent with `POST /api/restore`, the route that calls the Go `Restore`.
- The Rust master, on its own fresh SQLite store, restores the same bytes through
  `Master::restore`. `RustMaster::restore` in `conformance/src/cluster.rs` is the one
  addition: a harness method that calls it, because the master is private to the
  harness. Production code is unchanged.
- The test does not skip. A missing Go toolchain fails it in `GoBuild::shared()`.

Output (`cargo test -p gorse-conformance --test playground_restore -- --nocapture`):
