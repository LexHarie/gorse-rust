## Tests (`conformance/tests/playground.rs`)

| Test | Covers |
|---|---|
| `playground_ml_100k_go_dashboard_answers` | The Go `gorse-in-one --playground=ml-100k`: the config it writes, the welcome block, one download of the dump, `/`, `/overview` and `/apidocs/` answer 200, and `/api/users?n=3` gives `1`, `10`, `100`. |
| `playground_ml_100k_rust_dashboard_answers` | The same checks on the Rust `gorse-in-one`. |
| `playground_ml_100k_rust_matches_go` | The two runs compared: the lines before the server starts (the welcome block and the lines above it), the config bytes, the CDN requests, the dashboard status and body at each path, the users route and its first ids. |

Each build runs once per test process (`OnceLock`), and the runs are serialised under one lock, because both builds bind the playground's fixed ports (8086 and 8088).

## Harness changes

- `conformance/src/cluster.rs`: `GO_PACKAGES` gains `./cmd/gorse-in-one`, so the Go playground binary is built through `GoBuild::shared()`.
- `conformance/Cargo.toml`: dev-dependency `rustls` (workspace), for the stand-in's TLS server. `Cargo.lock` gains one line for it.

## Deviations

**D-WP53-1 The CDN stand-in (test harness, not production code).** Both binaries hard-code `https://cdn.gorse.io/example/` (`cmd/gorse-in-one/main.go:151-152`, `crates/gorse-cmd/src/in_one.rs` `PLAYGROUND_URL`), and neither reads an override. The test sends the download through `HTTPS_PROXY` to a loopback proxy. The proxy answers `CONNECT cdn.gorse.io:443` with a TLS session. Its certificate is for `cdn.gorse.io` and is signed by a test CA made for each run, and the binary trusts that CA through `SSL_CERT_FILE` (Go's `crypto/x509` and `rustls-native-certs` both read it). The proxy serves the bytes of `/mnt/project-files/datasets/ml-100k.bin.gz` at `GET /example/ml-100k.bin.gz`, as the CDN serves them. The binaries run unchanged, and their own download code runs. The stand-in records each request, and the test asserts one download, answered 200. Other hosts get 403.
This lifts the offline limit that WP-4-7 logged as D-WP47P-1 (`porting/notes/WP-4-7-playground.md`) for the conformance crate. The ignored binary test in `crates/gorse-cmd/tests/playground.rs:155` keeps its `#[ignore]`, as the court asked. Its data path is an open question (see below).

**X-WP53-1 The CPU line names the CPU brand in Go only.** Go prints `Using 4 CPU cores: Intel(R) Xeon(R) Processor @ 2.10GHz` (the cpuid brand name, `cmd/gorse-in-one/main.go`, `setup`). Rust prints `Using 4 CPU cores`. The Rust line lacks the brand, so this is a port gap in `crates/gorse-cmd/src/in_one.rs` (`use_playground_stores`), and it belongs to the owner of that file. The test compares both lines up to `CPU cores` and leaves the brand out. The core count is compared. The line is cosmetic: it is not part of a contract, and no REST or wire output depends on it.

**X-WP53-2 Log records print before the welcome block in Rust only.** Both builds write their logs as JSON lines on stdout. The Go build logs after the welcome block, because `setup` runs before `Serve`. The Rust build calls `serve()` before the import, so its tracing lines come first (`porting/notes/WP-4-5.md`, deviation 6). The test skips JSON lines when it reads the block, and it compares the playground's own lines only. The log records themselves are not compared, because their timestamps differ on every run.

## Not in this WP

- The data path. `scripts/setup-datasets.sh` does not place `.bin.gz` files, so this test reads `/mnt/project-files/datasets/ml-100k.bin.gz` directly, as `crates/gorse-cmd/tests/playground.rs` does. The script is unchanged. The court decides whether the test should read `~/.gorse/dataset` instead, after the script copies the `.bin.gz` files there.
- `playground_ml_100k_imports_the_dataset_and_serves` in `crates/gorse-cmd/tests/playground.rs:155` stays `#[ignore = "O-1: dataset from cdn.gorse.io"]`. This WP does not change it. This WP's stand-in could run it offline, if the court decides to un-ignore it.
- The other CDN datasets (`ml-1m`, `yelp`, and the rest of O-1) are not part of this WP.
