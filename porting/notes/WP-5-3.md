## Tests (`conformance/tests/playground.rs`)

| Test | Covers |
|---|---|
| `playground_ml_100k_go_dashboard_answers` | The Go `gorse-in-one --playground=ml-100k`: the config it writes, the welcome block, one download of the dump, `/`, `/overview` and `/apidocs/` answer 200, and `/api/users?n=3` gives `1`, `10`, `100`. |
| `playground_ml_100k_rust_dashboard_answers` | The same checks on the Rust `gorse-in-one`. |
| `playground_ml_100k_rust_matches_go` | The two runs compared: the lines before the server starts (the welcome block and the lines above it), the config bytes, the CDN requests, the dashboard status and body at each path, the users route and its first ids. |
| `playground_cdn_stand_in_serves_the_dump_unchanged` | The stand-in alone, through a client that trusts the test CA: status 200, `Content-Length` equal to the dump's length, and the body equal to the dump's bytes. This is the evidence that the bytes are right. |

Each build runs once per test process (`OnceLock`), and the runs are serialised under one lock, because both builds bind the playground's fixed ports (8086 and 8088).

## Data path (court ruling, 2026-11-02)

- The test reads `$HOME/.gorse/dataset/ml-100k.bin.gz`. It does not read `/mnt/project-files` directly, and it does not fall back to another copy. A missing file fails the test, and the panic says to run `scripts/setup-datasets.sh`.
- `scripts/setup-datasets.sh` now places that file. It takes the new `GORSE_DUMPS` list (default `ml-100k.bin.gz`) and copies each dump into `~/.gorse/dataset` as it is. The source is `$DATASETS_SRC/<name>` when that file exists, and otherwise `https://cdn.gorse.io/example/<name>`, the URL the playground downloads. A dump already in the folder is skipped, and nothing is overwritten. A failed fetch leaves no partial file.
- Evidence for the script (run in this container): with an empty `HOME`, the first run copies `ml-100k.bin.gz` from `/mnt/project-files/datasets/`, and `cmp` finds it equal to the project file. A second run prints `present: ml-100k.bin.gz`. With `DATASETS_SRC` empty and no local copy, the run fails with curl's 403 from the CDN, which is the expected result here, and `~/.gorse/dataset` holds no partial `.bin.gz`.
- `crates/gorse-cmd/tests/playground.rs:155` keeps its `#[ignore = "O-1: dataset from cdn.gorse.io"]`, as the court asked. Removing it is for the WP-5-4 audit.

## Deviations

**D-WP53-1 The CDN stand-in (test harness, not production code).** Both binaries hard-code `https://cdn.gorse.io/example/` (`cmd/gorse-in-one/main.go:151-152`, `crates/gorse-cmd/src/in_one.rs` `PLAYGROUND_URL`), and neither reads an override. The test sends the download through `HTTPS_PROXY` to a loopback proxy. The proxy answers `CONNECT cdn.gorse.io:443` with a TLS session. Its certificate is for `cdn.gorse.io` and is signed by a test CA made for each run, and the binary trusts that CA through `SSL_CERT_FILE` (Go's `crypto/x509` and `rustls-native-certs` both read it). The proxy serves the bytes of `~/.gorse/dataset/ml-100k.bin.gz` at `GET /example/ml-100k.bin.gz`, as the CDN serves them. The binaries run unchanged, and their own download code runs. The stand-in records each request, and the test asserts one download, answered 200. Other hosts get 403.
This lifts the offline limit that WP-4-7 logged as D-WP47P-1 (`porting/notes/WP-4-7-playground.md`) for the conformance crate. The ignored binary test in `crates/gorse-cmd/tests/playground.rs:155` keeps its `#[ignore]`, as the court asked.

**Bytes the Go download expects.** Go's `setup` (`cmd/gorse-in-one/main.go`) takes the response of `http.Get` on the CDN URL, reads `ContentLength` for its progress bar, and passes the body to `gzip.NewReader` and then `m.Restore`. The stand-in meets each of these. It answers 200 with `Content-Length` equal to the file's length, and its body is the file's bytes. The check is `playground_cdn_stand_in_serves_the_dump_unchanged`, which compares the body byte for byte. Two more facts show the Go path accepted the bytes: the Go import ran to its welcome block, and `/api/users?n=3` returned `1`, `10`, `100` from it, in the Go run and the Rust run alike.

**X-WP53-1 The CPU line names the CPU brand in Go only.** Go prints `Using 4 CPU cores: Intel(R) Xeon(R) Processor @ 2.10GHz` (the cpuid brand name, `cmd/gorse-in-one/main.go`, `setup`). Rust prints `Using 4 CPU cores`. The Rust line lacks the brand, so this is a port gap in `crates/gorse-cmd/src/in_one.rs` (`use_playground_stores`), and it belongs to the owner of that file. The test compares both lines up to `CPU cores` and leaves the brand out. The core count is compared. The line is cosmetic: it is not part of a contract, and no REST or wire output depends on it.

**X-WP53-2 Log records print before the welcome block in Rust only.** Both builds write their logs as JSON lines on stdout. The Go build logs after the welcome block, because `setup` runs before `Serve`. The Rust build calls `serve()` before the import, so its tracing lines come first (`porting/notes/WP-4-5.md`, deviation 6). The test skips JSON lines when it reads the block, and it compares the playground's own lines only. The log records themselves are not compared, because their timestamps differ on every run.
