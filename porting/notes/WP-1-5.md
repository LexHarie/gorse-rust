# WP-1-5 notes: common/heap

Provisional ids; the integrator renumbers them into `PORTING_NOTES.md` and
`PORTING.md`. The Rust module is `crates/gorse-common/src/heap.rs`; the Go
oracle data is `crates/gorse-common/tests/data/heap_golden.json`, written by
`contracts/tools/heapgolden`.

## Quirks reproduced

- **Q-WP15-1 `PriorityQueue.Pop` keeps the value in the lookup set.** `Push`
  ignores any value pushed before, so a value popped from a queue can never be
  pushed into it again (`pq.go:81-93`; `Pop` at `pq.go:96-99` never touches
  `lookup`). Reproduced; `popped_values_are_not_pushed_again` and the golden
  `bounded at 10` cases (the `ann.Bruteforce` push-then-pop pattern, values
  repeating) cover it.
- **Q-WP15-2 `PriorityQueue.Clone` does not copy the lookup set.** The copy
  starts with an empty set (`pq.go:117-122`), so pushing a value it already
  holds adds a second element with that value. `HNSW.searchLayer` clones its
  enter points this way. Reproduced as `clone_queue`; each non-empty golden
  case pushes up to three values the clone holds, plus random ones, and
  compares the heap array.
- **Q-WP15-3 `PriorityQueue.Unmarshal` trusts its input.** Any non-zero order
  byte means descending (Go's `binary.Read` into a `bool` is `b != 0`); the heap
  array is taken as written, without checking heap order or NaN weights;
  duplicate values are kept in the array while the lookup set holds each once.
  Reproduced; golden `unmarshal` cases cover each.
- **Q-WP15-4 `TopKFilter` accepts NaN weights.** Only `PriorityQueue.Push`
  rejects NaN. Weights compare with Go's `<`/`>`, false for NaN, so where a NaN
  ends up depends on the push order. Reproduced by comparing with `PartialOrd`
  operators (not `total_cmp`); the golden `nan=true` cases cover both
  instantiations.
- **Q-WP15-5 The Go doc comment of `PriorityQueue.Pop` says an empty queue
  returns an error; it panics** (index out of range in `container/heap.Pop`).
  See X-WP15-1 for what Rust does.

## Deviations

- **X-WP15-1 `pop` and `peek` on an empty `PriorityQueue` return `None`**
  where Go panics. Every Go caller checks `Len()` first (`common/ann/hnsw.go`,
  `common/ann/bruteforce.go`) or holds a queue that cannot be empty there, so no
  caller's behaviour changes; Rust callers write `.expect(..)` where Go relies
  on non-emptiness. Pushing a NaN weight still panics with Go's message, as
  does `reverse` of a queue holding one.
- **X-WP15-2 `PriorityQueue::unmarshal` returns a new queue.** Go's
  `Unmarshal` fills an existing queue and on an error leaves it half-written
  (order byte set, `elems` replaced by a zeroed slice of the declared length,
  lookup set stale). The only caller, `HNSW.Unmarshal`, creates a fresh queue
  for each call and discards everything on an error. A negative element count
  is an error, where Go panics in `makeslice` (as `PORTING_NOTES.md` X-7).
- **X-WP15-3 `TopKFilter::new` takes `usize`.** Go takes an `int`; a negative
  `k` keeps nothing, exactly as `k = 0` (golden `k=-1` cases, replayed with
  `k = 0`). A caller holding a signed value passes
  `usize::try_from(k).unwrap_or(0)`.
- **X-WP15-4 Methods promoted from Go's unexported `_heap` are not ported.**
  `Less` and `Swap` on both types, and `Pop() any` on `TopKFilter` (which
  removes the last array element, not the top), are callable from other Go
  packages but no Gorse code calls them.
